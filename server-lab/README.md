# MARCOSA R28 — реальный серверный контур, локальное испытание

Это отдельный исполняемый Node.js 22+ сервер. В отличие от статического GitHub Pages, он действительно хранит пользователей, персональные миры, черновики, публикации и жалобы, соблюдая авторство. Но это **исследовательская лаборатория**, а не боевая социальная сеть.

## Быстрая проверка

В корне репозитория:

1. node --test server-lab/test/core.test.mjs
2. Сгенерируйте приватный код приглашения: openssl rand -hex 24
3. Введите его в переменную окружения MARCOSA_INVITE_CODE, не публикуя в GitHub или чате.
4. node server-lab/server.mjs
5. Откройте http://127.0.0.1:8787, создайте аккаунт по приглашению, войдите и опубликуйте запись в своём мире.

По умолчанию база данных хранится в оперативной памяти и очищается после завершения сервера. Для локальной записи на диск сначала создайте приватный каталог .local, затем укажите переменную MARCOSA_DB_PATH со значением ./.local/marcosa.sqlite. Никогда не коммитьте содержимое этого каталога.

## Реальные функции

- POST /api/auth/register — приглашения, валидация, индивидуальный scrypt-хэш пароля и автоматическое создание личного мира в одной транзакции.
- POST /api/auth/login и /api/auth/logout, GET /api/auth/me — случайный токен сессии; сервер хранит только его SHA-256, браузер получает HttpOnly и SameSite=Strict cookie.
- GET /api/worlds и POST /api/worlds — миры с владельцами, лимит три мира в лаборатории.
- GET /api/posts и GET /api/worlds/:slug/posts — публичные публикации с пагинацией; приватные черновики сюда не попадают.
- GET /api/me/posts, POST /api/posts, PATCH/DELETE /api/posts/:id — личные черновики, публикация, снятие и удаление с проверкой автора.
- POST /api/reports и GET /api/mod/reports, POST /api/mod/posts/:id/hide — реальные жалобы и доступ модератора, не открытый обычным пользователям.
- GET /api/account/export — выгрузка только своих миров, черновиков, публикаций и поданных жалоб, без паролей и сессий.
- DELETE /api/account — повторный ввод пароля, подтверждение DELETE и каскадное удаление данных этого пользователя.
- Интерфейс server-lab/public/ с реально работающим входом, лентой, редактором, персональными мирами, жалобами и управлением аккаунтом.

## Защитные границы

- Сервер запускается только на локальном интерфейсе 127.0.0.1 / ::1; попытка запустить на 0.0.0.0 завершится ошибкой.
- Для изменяющих запросов проверяется Origin и JSON content type, действуют лимиты запроса, действий и размеров контента.
- Динамические данные отображаются исключительно через textContent; нет вставки чужого HTML.
- Роль модератора не присваивается клиентом. Без подтверждения электронной почты нельзя безопасно повышать роль только по совпадению адреса.
- Сессионные cookie предназначены для локальной разработки без HTTPS. Этот конфиг нельзя без изменений публиковать через внешний reverse proxy.

## Не реализовано для production

Email verification, парольное восстановление и MFA; распределённый антиспам; аудит администраторов; GDPR-процессы; резервное копирование и мониторинг; защита от DDoS; медиа и личные сообщения; реальные World Roles; управление жалобами с апелляциями.

По PRODUCT BIBLE целевая архитектура — Supabase Auth и PostgreSQL с RLS. **Подключённый Supabase сейчас не содержит доступных проектов**, поэтому таблицы production и RLS не менялись. SQLite здесь используется только для испытаний API-контракта. Не импортировать production-данные в лабораторию.

## Путь к закрытой бете

1. Идентифицировать действующий проект MARCOSA и проверить существующий Supabase Auth, таблицы и RLS. Не создавать дубликат продакшен-БД без подтверждения.
2. Перенести проверенный API-контракт в Postgres/RLS, тестировать двух пользователей и модератора отдельными JWT; включить email verification, CSRF-защиту за HTTPS, rate-limit в Redis и аудит.
3. Подготовить отдельный STAGING с надёжно проверенным SSH host key и TLS. Не отключать StrictHostKeyChecking.
4. Только после независимого аудита безопасности запускать закрытую многопользовательскую бету.

Публичная MARCOSA Pages продолжает работать без изменений. R28 не заявляется опубликованной боевой соцсетью.


## R30 — реальные сообщества и двусторонний рекламный пилот (локально)

R30 расширяет локальную лабораторию R28, не меняя публичный GitHub Pages и не открывая сервер в интернет.

**Серверные функции:**
- GET /api/worlds — реальные счётчики опубликованных записей и подписчиков из SQLite, без искусственных просмотров.
- GET /api/worlds/:slug/followers, POST/DELETE /api/worlds/:slug/follow — подписки на чужие Worlds. Нельзя подписаться на свой мир или накрутить двойную подписку.
- GET/POST /api/posts/:id/comments и DELETE /api/comments/:id — обсуждения только опубликованных записей. Скрытые комментарии не видны; удаляет автор.
- POST /api/comments/:id/report, GET /api/mod/comment-reports, POST /api/mod/comments/:id/hide — отдельная очередь жалоб и модерация.
- POST /api/sponsors/proposals — заявитель предлагает тестовое спонсорство ЧУЖОМУ World. Ссылка — только общедоступный HTTPS-домен, без автоматической оплаты.
- GET /api/me/received-sponsors, POST /api/sponsors/:id/creator-decision — владелец целевого World принимает или отклоняет заявку.
- GET /api/mod/sponsors, POST /api/mod/sponsors/:id/review — только после согласия владельца World независимый модератор может допустить тестовое размещение. Ни заявитель, ни владелец World не могут сами одобрить итог.
- GET /api/sponsors/approved — только явно рассмотренные предложения с обязательным дисклеймером «ТЕСТОВОЕ РАЗМЕЩЕНИЕ · НЕ ОПЛАЧЕНО».
- GET /api/account/export — исходящие заявки, подписки, комментарии, посты; удаление аккаунта каскадно удаляет связанные личные данные.

**Не реализованы для коммерции:** проверка юридических рекламодателей, права на бренд, договоры, оплата, инвойсы, RPM/CPM, viewability, биллинг, возвраты, реальные просмотры, fraud-detection и публичный Ads Manager. Нельзя выдавать возможности лаборатории за действующие платные показы.

**CI:** node --test server-lab/test/core.test.mjs server-lab/test/r30.community_ads.test.mjs. Chromium 1440/390/360: настоящие регистрация, вход, публикация, комментарий, подписка и заявка.

**Postgres:** docs/MARCOSA_R30_POSTGRES_RLS_REFERENCE.sql — только reference для ревизии, не миграция и не исполненный SQL. Перед использованием обязательны доступ к проверенному Supabase-проекту, подтверждённая RLS, защищённая Auth и независимый STAGING.

## R31 — персональная лента и приватный центр активности (локальная лаборатория)

- `GET /api/feed/following?limit=12&cursor=...`: строго авторизованная лента опубликованных постов из Worlds, на которые пользователь реально подписан. Снятие подписки немедленно убирает записи из персональной выдачи. Чужие черновики или скрытые модератором записи никогда не включаются.
- `GET /api/me/activity?cursor=...`: только события текущего аккаунта (20 на страницу) и реальный `unreadCount`. Другому пользователю не выдаётся даже наличие чужих событий.
- `POST /api/me/activity/read`: отмечает прочитанными **только свои** события; требует текущую сессию, JSON и same-origin.
- Реальные события: новая подписка, ответ на запись, предложение тестового партнёрства, согласие/отказ создателя, независимое решение модератора, отзыв предложения. Источники и события записываются в одной SQLite транзакции. Дублирующая подписка не создаёт повторных уведомлений; собственные действия не являются уведомлениями.
- `GET /api/account/export` включает принадлежащую пользователю историю активности без паролей и токенов. Удаление связанных аккаунтов, Worlds, постов или рекламных заявок каскадно удаляет соответствующие события. Для каждого личного inbox сохраняются последние 250 событий.
- Интерфейс `Мои подписки` работает только после входа; `Моя активность` отображается исключительно для авторизованного владельца аккаунта. Все имена и подписи создаются через `textContent`.
- Проверка: `node --test server-lab/test/core.test.mjs server-lab/test/r30.community_ads.test.mjs server-lab/test/r30.migration.test.mjs server-lab/test/r31.following_activity.test.mjs`. Новый тест реально поднимает loopback HTTP сервер с отдельными пользователями и проверяет права, скрытые черновики, отметку прочитанного, экспорт и удаление данных.

Важно: SQLite inbox R31 не предназначен для production. Нет push/email уведомлений, долговременных дистрибутивных очередей, полной GDPR-эксплуатации или аналитики рекламных показов. Нужны проверенные Supabase Auth + PostgreSQL/RLS и независимый STAGING. 

## R32 — независимая апелляция и журнал модерации (локально)

- Скрытие публикаций/комментариев модератором теперь атомарно фиксирует действие в `moderation_audit` и соответствующее обновление жалоб. Невозможно скрыть собственную публикацию как модератору.
- Автор скрытого поста или комментария может подать личную апелляцию через `POST /api/appeals` с `kind=post|comment`, `subjectId` и причиной от 12 до 1000 символов. Не больше одного открытого обращения на предмет одновременно; базовое локальное ограничение частоты.
- Автор видит свои скрытые материалы и решения на `GET /api/me/moderation`. Другие участники и посетители этих данных не видят.
- Очередь `GET /api/mod/appeals` и `POST /api/mod/appeals/:id/resolve` доступны только модератору. **Проверяющий не может быть ни заявителем, ни тем модератором, который изначально скрыл контент.**
- Решения `restored` или `upheld` атомарно сохраняют результат; при `restored` публикация/комментарий снова доступен публично (если его родительская запись видима). После решения второй раз его изменить нельзя.
- `GET /api/mod/moderation-audit` возвращает последние 50 действий модерации только модераторам, без лишних персональных сведений. Экспорт аккаунта включает **только собственные** апелляции. FK-каскад удаляет связанные записи при удалении владельца и/или его контента.
- UI: аккуратное обращение с формой причины, история собственных обращений, очередь модератора и журнал без HTML-инъекций.
- Автотест `test/r32.moderation_appeals.test.mjs` использует 4 настоящие учётные записи в изолированном HTTP+SQLite тесте; проверяет независимость, подмену источника, права доступа, восстановление, подтверждение скрытия, экспорт и целостность FK.

Ограничения: это исследовательская лаборатория, а не публичная система юридических апелляций. Не реализованы SLA модерации, удалённый multi-region аудит, хранение доказательств, реестр регуляторных обращений, production identity и Postgres RLS. До приглашения реальных пользователей необходимы защищённый STAGING и правовая политика с независимой проверкой.

## R34 — реальный резервный снимок SQLite и проверенное восстановление (только локально)

Команды после остановки локального сервера или для консистентного online-backup:

```sh
node server-lab/tools/lab-snapshot.mjs backup .local/marcosa.sqlite .local/marcosa-backup.sqlite
node server-lab/tools/lab-snapshot.mjs restore .local/marcosa-backup.sqlite .local/marcosa-restored.sqlite
```

**Результат:** CLI создаёт новый файл через встроенный SQLite Backup API, проверяет `PRAGMA integrity_check`, `PRAGMA foreign_key_check` и присутствие обязательной схемы MARCOSA, пишет права `0600`, считает SHA-256 и публикует файл атомарно через create-only hardlink. Restore повторно проверяет копию, создаёт только НОВЫЙ файл и никогда не перезаписывает рабочий. Запрещены symlink-источники, существующие назначения, другие расширения и повреждённые файлы.

- Тест `server-lab/test/r34.snapshot.test.mjs` проверяет настоящую дисковую БД с персональными данными, точное восстановление, защиту от перезаписи, повреждённой копии, символьной ссылки и сохранность паролей (хэши не печатаются в отчёт).
- Снимки **включают данные аккаунтов, сессии, соль и парольные хэши** — это конфиденциальные файлы. Не выкладывать их в репозиторий, GitHub Actions artifacts, публичный сайт, почту или чат. Хранить в закрытом каталоге с отдельной политикой доступа и шифрованием диска.
- Для восстановления на действующий локальный сервер сначала выключить приложение, создать защищённую копию исходного файла, проверить новый файл отдельно и только затем выполнить плановую замену через оператора; CLI специально не делает in-place restore.

**Не путать с production:** это не заменяет PITR, offsite резервирование, автоматизированные политики хранения, Redis/Media Storage бэкапы или реальный DR drill PostgreSQL. R34 доказателен только для SQLite лаборатории.

## R36 — защита localhost от DNS rebinding и подмены Host

R36 не превращает локальную лабораторию в публичный сервер. Напротив, он закрывает опасный сценарий, в котором внешний сайт направляет браузер на `127.0.0.1` через управляемое доменное имя.

- **Все HTTP-маршруты**, включая `GET /api/health`, отклоняют `Host`, не равный `localhost`, `127.0.0.1` или `[::1]`. Если в Host указан порт, он обязан совпадать с фактическим портом слушателя.
- Сетевая пара `remoteAddress/localAddress` проверяется на loopback. Не доверяем `X-Forwarded-For`, непроверенному reverse proxy или Host.
- Любое изменение данных по-прежнему требует HTTP `Origin`, в точности совпадающего с `http://<Host>` и допустимым JSON; чужие сайты не могут переключать роль/сессию, отправлять комментарии или заявки.
- Проверка через `node --test server-lab/test/r36.loopback_security.test.mjs` посылает настоящие необработанные HTTP-заголовки: опасные домены, `localhost.evil.example`, ложные порты, внешние Origin, отсутствие Origin, допустимый localhost/IPv6 Host.
- Даже прошедший R36 **не разрешает** внешний запуск сервера. Для production нужна отдельная Auth/HTTPS/CSRF/проверка IP у reverse proxy, без переноса этой локальной схемы в интернет.

Это ещё один обязательный регрессионный тест в CI, а не заявление о завершённом security audit.

## R38 — World Builder: настоящее изменение названия и описания (только localhost)

Теперь владелец может раскрыть «Редактировать оформление моего мира» в личном кабинете, выбрать один из своих Worlds, изменить название и описание и сохранить. Публичный список Worlds, Discover и личный профиль читают те же сохранённые данные SQLite.

- `PATCH /api/worlds/:slug` защищён реальной сессией, строгим Origin, JSON и `owner_id` в SQL `WHERE`.
- Разрешены **только** `title` (3–70 символов) и `description` (до 400). Нельзя передать/поменять `slug`, `ownerId`, права или поля другого человека.
- slug и авторство остаются неизменными, опубликованные посты не отрываются от World; текст отображается безопасно через `textContent`.
- Регрессионный тест `server-lab/test/r38.world_owner_studio.test.mjs` проверяет двух реальных пользователей, отказ гостю и чужому аккаунту, CSRF, попытку сменить slug, ошибки длины и публичную выдачу после записи.
- Настоящий Chromium E2E редактирует World и подтверждает сохранение на экранах 1440, 390 и 360 px; новая серия из 18 кадров. Отдельная проверка `.github/workflows/marcosa-r38-world-studio.yml` защищает этот контракт от регрессий.

**Граница реализации:** в R38 нет загрузки фото/видео, смены владельца, коллаборативных ролей, production-bucket и подключённого Supabase. Это реально работающий локальный редактор мира, но пока не глобальная онлайн-публикация.

## R39 — управление безопасностью аккаунта и ключами входа (локально)

Реализован **проверяемый** раздел «Безопасность аккаунта». Он намеренно не превращает MARCOSA в публичную систему аутентификации: это изолированная SQLite-лаборатория.

- `GET /api/me/security`: только текущий вошедший пользователь получает количество действующих сессий и срок текущей; emailVerified и recoveryConfigured явно `false`. Никогда не возвращаются пароли, соли, токены или их хэши.
- `POST /api/me/security/revoke-others` с `currentPassword`: после scrypt-проверки текущего пароля удаляет все другие сессии **только этого** пользователя. Текущая сессия остаётся активной.
- `POST /api/me/security/change-password` с `currentPassword` и `newPassword`: требует новый пароль 12–128 символов, отличный от старого; пересчитывает scrypt с новой случайной солью. **Одной SQLite транзакцией** обновляет пароль и удаляет все сессии пользователя, включая текущую. Возвращает очищающую HttpOnly SameSite=Strict cookie. Никакого автоматического повторного входа.
- Операции требуют loopback Host (защита R36), строгий same-origin и JSON, существующую сессию и лимит попыток. Другой пользователь остаётся вошедшим.
- Интерфейс: актуальный счётчик сеансов, форма выхода с других устройств, безопасная смена пароля, явное предупреждение, что email-recovery пока нет. Поля паролей очищаются.
- Настоящий HTTP E2E `test/r39.account_security.test.mjs`: два разных владельца, несколько сессий, неверный пароль, отклонение чужого Origin, повторные входы, проверка смены scrypt соли, полная аннуляция токенов и privacy-экспорт.
- Настоящий Chromium `test/browser-cdp.mjs`: 1440/390/360, после реального World Builder и социальной активности выполняет кнопки безопасности, меняет пароль, убеждается, что старый пароль больше не работает, а новый работает; 21 снимок UI.

Важно: для production нельзя использовать этот механизм вместо Supabase Auth; не обеспечены verified email, MFA, password recovery, managed session revocation, global abuse rate limiting, TLS, shared sessions, RLS с реальными JWT. Для перехода на production требуется соответствующий отдельный security review.

## R40 — настоящая блокировка аккаунтов (только локальная лаборатория)

В раздел «Блокировки и защита сообщества» добавлены функции, которые действительно изменяют состояние SQLite, а не только скрывают кнопку.

- `GET /api/me/blocks`: только вошедший пользователь видит свой список из максимум 100 заблокированных авторов; ни пароли, ни идентификаторы аккаунтов, ни чужие списки блокировок не возвращаются.
- `POST /api/users/:username/block`: создание личного ограничения с защитой от блокировки самого себя и ограничением частоты. При первой блокировке **в одной транзакции** удаляются все взаимные подписки и прежние личные события, активные взаимные рекламные заявки переходят в `revoked`.
- `DELETE /api/users/:username/block`: снятие собственного запрета. Прошлые подписки, удалённые события и аннулированное согласие **не восстанавливаются**; стороны могут подписаться заново.
- Для вошедших аккаунтов SQL фильтрует Worlds, Discover, публикации, личную ленту подписок, обсуждения и тестовые рекламные предложения в обе стороны. Анонимная публикация намеренно не меняется: **блокировка не превращает публичный World в приватный**.
- Попытки подписываться, писать комментарии или предлагать рекламную кампанию другой стороне блокировки отклоняются с 403, даже если атакующий сохранил ID поста или публичный slug.
- Клиентский UX: «Заблокировать автора» в карточке чужого World, управляемый личный список и «Разблокировать»; все подписи создаются через `textContent`.
- `test/r40.community_blocks.test.mjs`: независимые Alice/Bob/Carol, настоящий HTTP, проверка односторонней блокировки с двусторонним запретом взаимодействия, проверка списков гостей/участников, удаление подписок/уведомлений, немедленный отзыв рекламы, повторная подписка после снятия, FK-каскад при удалении аккаунта.
- `test/browser-cdp.mjs`: регрессионный браузерный прогон всех существующих социальных функций, аккаунтов и нового интерфейса блокировок на ПК и экранах 390/360 px (21 кадр). Само блокирование отдельно проверяется реальными HTTP-запросами в R40.

**Ограничения:** R40 не является защитой от анонимного чтения публичного контента, не обеспечивает IP-блокировку и не заменяет централизованную модерацию. В production блокировки должны работать в Postgres под проверенными JWT, вместе с необходимыми RLS-политиками, механикой жалоб и бизнес-требованиями.

## R42 — персональная коллекция сохранённых публикаций (реальные данные)

В локальной социальной лаборатории появилась полноценная функция «Моя коллекция сохранённых публикаций»: можно сохранить полезную историю, перечитать позже, удалить из коллекции и листать историю сохранений. Нет искусственных реакций, показов или скрытого рекламного трекинга.

- `POST /api/posts/:id/save`: настоящий авторизованный HTTP-запрос, разрешает сохранить только существующую опубликованную запись, доступную текущему пользователю с учётом блокировок. Повторный запрос идемпотентен.
- `DELETE /api/posts/:id/save`: пользователь удаляет только собственную связь сохранения, даже если оригинальная запись позже скрыта модерацией или заблокирована для просмотра.
- `GET /api/me/saved`: приватная отсортированная SQLite-коллекция с реальной пагинацией через ID сохранения; не возвращает скрытые материалы и авторов, недоступных из-за блокировок. По 20 записей; исходные публикации продолжают принадлежать создателям.
- `GET /api/me/saved/ids`: собственный набор сохранённых ID для корректных состояний кнопки «Сохранить / Сохранено» во всех карточках. Список ограничен 500 элементами.
- Функция не раскрывает список чужих сохранений и не создаёт публичных метрик. Новая таблица `saved_posts` имеет уникальный ключ user/post и FK-каскад на пользователя и оригинальную публикацию.
- Экспорт `GET /api/account/export` дополнен `savedPosts`, только для владельца. Удаление исходной записи или аккаунта физически удаляет соответствующие строки.
- Трёхаккаунтный реальный HTTP-тест `test/r42.bookmarks.test.mjs` проверяет дубликаты, пагинацию, запрет гостям, безопасность блокировок, исходные черновики, скрытие модерацией, удаление и FK.
- Реальный Chromium-сценарий проверяет сохранение из ленты, появление в персональной коллекции и отмену с контролем содержимого на 1440, 390, 360 px.

Важно: это лабораторная SQLite-реализация; **не** PostgreSQL production-код и **не** материал для отключения существующих прав модерации. Настоящее хранилище Supabase пока не подключено. Для переноса нужны отдельные owner-only RLS, подтверждённые JWT, логирование ошибок и наблюдаемость закрытой беты.

## R45 — управляемая закрытая бета и первые 5 шагов автора

R45 добавляет настоящие одноразовые приглашения к локальному Node/SQLite серверу. Это **не** Supabase Auth и не общедоступный запуск MARCOSA.

**Режимы регистрации (переменная `MARCOSA_REGISTRATION_MODE`):**

- `legacy` (по умолчанию ради совместимости с R28): прежний `MARCOSA_INVITE_CODE` разрешает многократный вход, а одноразовые коды модератора тоже работают. **Не использовать legacy для публичной закрытой беты**, поскольку общий код многоразовый.
- `single-use`: строго только отдельно выданные одноразовые коды с 48 hex-символами и истечением 1–168 часов. Старый общий код **не принимается**.
- `closed`: любая регистрация отключена, даже если приглашение ранее создано. Активные локальные аккаунты могут входить.

**Контролируемая первичная настройка на своей машине:**

1. Остановить сервер и подготовить приватную папку `.local/`. Запустить `legacy` с сильным случайным `MARCOSA_INVITE_CODE` и зарегистрировать **один** заранее проверенный аккаунт оператора.
2. Остановить сервер; создать защищённый backup через `node server-lab/tools/lab-snapshot.mjs backup .local/marcosa.sqlite .local/pre-operator.sqlite`.
3. Ограничить права: `chmod 600 .local/marcosa.sqlite` (Linux/macOS), затем `node server-lab/tools/bootstrap-moderator.mjs .local/marcosa.sqlite YOURUSERNAME --confirm-offline`.
4. CLI проверяет целостность SQLite, файл, отсутствие символьных ссылок, существующего модератора, права файла; только первый оператор может быть назначен таким способом. После повышения все его сессии отзываются.
5. Запустить сервер с `MARCOSA_REGISTRATION_MODE=single-use`. Теперь оператор входит повторно, раскрывает «Одноразовые приглашения» в кабинете модератора, выбирает метку и TTL 1–168 часов. Секрет показывается **один раз**, в SQLite сохраняется только SHA-256.
6. Выдавать код адресно по защищённому каналу; не помещать его в URL, внешнюю аналитику, логи, screenshots или публичный issue. Получатель использует существующую форму регистрации. Повторное использование, просроченные и отозванные коды отклоняются. Ошибка регистрации с занятым username не сжигает действующий код: всё происходит в одной SQLite транзакции.
7. В списке модератора видны только метаданные собственных приглашений и факт использования. Коды повторно не показываются. Владелец может отозвать ещё не использованное приглашение.

**Настоящий onboarding:** в профиле теперь пять шагов, считаемых SQL по действиям текущего владельца: заполненное описание мира, первая опубликованная запись, подписка на чужой мир, ответ другому автору и сохранённая история. Показатели не включают рекламные просмотры, фиктивную выручку, D7 и скрытые аналитические профили.

**Испытания:** `node --test server-lab/test/r45.pilot_onboarding.test.mjs`: регистрация по реальному одноразовому коду, ошибка дубликата с сохранением права, конкурентная попытка повторного использования, истечение TTL, отзыв, недоступность чужих приглашений, проверка чек-листа и очистка после удаления аккаунта. Дополнительно Chrome на 1440/390/360 px показывает корректный прогресс автора, оператор выдаёт код, один раз погашает и скрывает секрет до снимка экрана.

**Не реализовано:** управление реальными Supabase JWT, подтверждение email, MFA, автоматическая рассылка и социальное приглашение на адрес, платежи, реальный production cohort и массовая регистрация. Это закрытая инженерная лаборатория, а не безопасность глобального сервиса.

## R47 — настоящая статистика закрытой беты, без искусственных метрик

- `GET /api/mod/pilot-metrics` строго требует серверную роль `moderator`. Гости и обычные авторы получают 401/403. Ответ **не содержит** электронных адресов, имён пользователей, паролей, хэшей, токенов и секретов приглашений.
- Из одной и той же SQLite базы рассчитываются реальные количества: аккаунты участников, зарегистрировавшиеся по одноразовому приглашению, опубликовавшие авторы, опубликованные миры, ответы *другим авторам*, текущие связи подписки, сохранённые ссылки, выданные и использованные коды. Доли активации показываются только с явным знаменателем; при нуле используется `null`.
- D7/D30, реальные рекламные показы, охваты и платёжная выручка **не собираются и всегда возвращаются как `null`**. Запрещено трактовать `sessions` или `posts` как доказательство retention/DAU.
- При удалении аккаунта текущие показатели пересчитываются из оставшихся строк; исторически погашенное приглашение не становится повторно действительным. Индивидуальные данные пилота не экспортируются в маркетинговые метрики.
- Интерфейс оператора содержит сетку показателей с честным объяснением ограничений. Кнопка «Пересчитать» не обращается к сторонним сетевым сервисам и не создаёт показов.
- Регрессия `server-lab/test/r47.pilot_metrics.test.mjs` поднимает настоящую локальную БД, трёх авторов и оператора, создаёт приглашение, публикует реальные записи, подписку, ответ, сохранение, скрытие модератором и удаление аккаунта. Числа сравниваются с ожидаемыми фактами; чужой доступ и выдуманные D7/выручка запрещены.
- Chromium демонстрирует агрегаты на desktop/390/360 px после реального погашения кода.

**Не production:** это не удостоверенные рекламные измерения, не сквозная продуктовая аналитика и не замена настоящему Postgres/Auth. Для использования в реальном сервисе требуются согласия пользователей, безопасность метрик при малых когортах, retention event model, меры против накрутки, observability и интервью с аудиторией.

## R50 — персональные настройки входящих событий

В локальной социальной платформе теперь можно управлять тем, какие **будущие** события сохраняются в личную ленту уведомлений. Это работающая настройка на стороне сервера, а не визуальное скрытие карточки.

- `GET /api/me/notification-settings`: только вошедший владелец получает три булевых переключателя `follows`, `comments`, `sponsorships`. По умолчанию всё включено, но старые аккаунты мигрировать не нужно.
- `PATCH /api/me/notification-settings`: частичное или полное изменение настроек, строго JSON boolean и только три известные поля; same-origin и настоящая HttpOnly-сессия обязательны. SQL `ON CONFLICT` сохраняет результат по `user_id`, чужие настройки неизменны.
- Действительный `recordActivity` проверяет выбор получателя перед вставкой уведомления. Подписки, ответы и рекламные предложения всё равно выполняют свои легальные действия, но отключённый вид события больше не добавляется в персональную ленту.
- **Старые события не уничтожаются** при отключении категории; повторное включение влияет только на будущие события.
- Экспорт аккаунта теперь содержит `notificationSettings` без cookie, соли пароля и приватных токенов. Удаление аккаунта каскадно удаляет личную строку предпочтений.
- UI находится в кабинете и сохраняет настройки через реальный API. Email и push не отправляются и честно не заявлены как реализованные.
- `test/r50.notification_preferences.test.mjs`: три живых аккаунта, реальные подписки, комментарии, рекламные предложения, проверка отключения, повторного включения и прежних событий, неверных типов, CSRF, экспорта, перезапуска SQLite и FK-каскада.

**Граница:** проект всё ещё привязан к localhost и SQLite. Для production необходим отдельный owner-only PostgreSQL/RLS контракт, настоящие Auth/JWT и требования уведомлений при масштабировании. Никаких настоящих email/push, рекламных просмотров, оплаченной доставки здесь нет.

## R52 — тематики Worlds и управляемый поиск

Это реальная пользовательская функция изолированной соцсети MARCOSA: каждый владелец может присвоить своему World одну из семи тематик. Категория хранится в SQLite, а поиск фильтруется на сервере, с сохранением действующих блокировок и запрета на доступ к чужому миру.

- `GET /api/world-topics`: единый справочник `general`, `art`, `technology`, `business`, `education`, `lifestyle`, `travel` с русскими подписями. Интерфейс получает его от сервера, а не поддерживает дублирующиеся произвольные классификаторы.
- `POST /api/worlds` и `PATCH /api/worlds/:slug`: строго разрешённая категория, неизменность адреса и владельца; менять категорию может только владелец World.
- `GET /api/worlds?category=travel` и `GET /api/discover?q=city&category=technology` проверяют категорию, выполняют фильтрацию по SQL и применяют существующее разграничение блокировок. Поиск без категории остаётся совместим с R30–R50.
- Новые поля категорий и индекс добавляются к существующей SQLite через безопасный `ALTER TABLE`: предыдущие Worlds и их описания не стираются, получают категорию `general` и переживают повторный запуск.
- В интерфейсе: тематика при создании/редактировании, тонкая редакционная подпись в публичных карточках, выпадающий фильтр в Discover, мобильные размеры и премиальная сдержанная стилистика.
- Испытания `test/r52.world_topics.test.mjs` и `test/r52.legacy_world_upgrade.test.mjs`: публичные фильтры, реальные опубликованные материалы, другое имя владельца, отказ чужому пользователю, неверные значения, блокировки, миграция и индекс.

Это **не** платный контент-маркетплейс и не алгоритм рекомендаций по скрытому профилированию. Нет просмотров, рекламных платежей или живого Supabase. Для production необходимы отдельная миграция, JWT/RLS и нагрузочная приёмка.
