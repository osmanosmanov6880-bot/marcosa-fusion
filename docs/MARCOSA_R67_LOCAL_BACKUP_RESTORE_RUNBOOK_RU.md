# MARCOSA R67 — проверяемое резервное копирование и восстановление локальной SQLite-базы

**Сфера:** только локальная лаборатория MARCOSA (Node 22, SQLite, loopback). Не является production Backup/PITR и не разрешает публичный запуск.

## Реальные команды

```sh
node ops/local-backup-restore.mjs backup --db ./private/local.sqlite --out ./private/snapshot.sqlite
node ops/local-backup-restore.mjs restore --backup ./private/snapshot.sqlite --manifest ./private/snapshot.sqlite.json --out ./private/restored.sqlite
```

Источник всегда указывается явно. Для восстановления **обязательно новое имя файла**: существующая база никогда не перезаписывается. Восстановление не запускает внешний сервер и не меняет оригинальную базу.

## Реальные гарантии локального инструмента

- Из текущей SQLite делается согласованный snapshot через `VACUUM INTO` на том же хосте; исходный файл не модифицируется.
- До и после копирования выполняются `PRAGMA integrity_check` и `foreign_key_check`, проверяются ключевые таблицы пользователей, медиа, жалоб и согласий беты.
- Каждая копия получает SHA-256 и JSON-манифест, не содержащий персональных данных пользователей. При восстановлении сверяются размер и хеш, затем целостность на временном файле.
- Временный файл и итоговая копия создаются только с правами владельца (`0600`). Завершение атомарным переименованием; отказываем при пересечении путей, симлинках, существующих целях и подделанном манифесте.
- GitHub Actions выполняет настоящую проверку: создаёт тестовую локальную базу с пользователями, обложкой PNG/BLOB и согласиями, копирует и восстанавливает, сверяет данные, проверяет испорченную копию, symlink и запрет перезаписи. Это не мок облачного backup API.

## Ограничения и эксплуатационный этап

Копия **не зашифрована**. Её следует хранить только в защищённом локальном каталоге или зашифрованном хранилище вне исходного сервера; утилита не загружает данные в сеть. Нет автоматического расписания, offsite, шифрования ключами KMS, PITR, многорегионального восстановления и согласованного бэкапа Supabase Storage. Для реального production необходимо отдельно проверить RTO/RPO, backup/restore PostgreSQL+Storage в изолированном окружении, защиту ключей и процедуру удаления данных.
