# MARCOSA R180 — проверяемый NO-GO реальной staging-инфраструктуры

Дата: 19 ноября 2026 · PR #168 · feature/marcosa-r150-growth-economics

## Пять полных инженерных блоков

1. **Классификатор происхождения доказательств** (`ops/r180/evidence-classifier.mjs`). Строгая схема R179 отчёта и source-bundle SHA; проверяется исходный digest и каждая негативная оговорка `actualAwsReplicaVerified=false`, `actualGitHubReviewersVerified=false`. Пять недостающих внешних проверок получают фиксированные машиночитаемые коды. Единственное допустимое решение: `NO_GO_EXTERNAL_EVIDENCE_PENDING`. Контроль изменения полей, срока действия и SHA-256.
2. **Двойная подпись решения NO-GO** (`ops/r180/quorum-attestation.mjs`). Ed25519 и два **разных** закреплённых SPKI fingerprints; подписи проверяют точные байты packet, GitHub run, source commit, bundle и R179 SHA. Отвергаются одинаковые ключи, изменённые поля, истёкший packet и подмена подписей. В CI ключи временные: они **не доказывают существование двух разных людей** или реальных согласований среды.
3. **Защитный контроллер** (`ops/r180/hold-gate.mjs`). До и после записи несколько независимых чтений R179 из PostgreSQL; сверка классификации с исходным отчётом; проверка реальной (в CI одноразовой) таблицы закрытого карантина `r167_ci.r167_quarantine`; сравнение `generation`; отдельный readback сохранённого NO-GO. Ошибки приводят к отказу и попытке записи инцидента. Нет методов деплоя.
4. **Native PostgreSQL17 append-only hold** (`tests/postgres/181_r180_no_go_hold.sql`, `ops/r180/hold-ledger.mjs`). `NOLOGIN` writer, `FORCE ROW LEVEL SECURITY`, только SELECT/INSERT, NO UPDATE/DELETE, защита веб-ролей, `SERIALIZABLE`, уникальный run/nonce и `id=1`, строгая JOIN-проверка R179 evidence + audit + R178 root. Решение навсегда остаётся NO-GO в рамках этого контейнера. Отдельная атомарная таблица аудита.
5. **Приёмка и восстановление** (`ops/test/r180.no-go.test.mjs`, `ops/r180/ci-acceptance.mjs`, workflow R180): негативные тесты ложных AWS/GitHub признаков, stale-данных, дублированных подписей, ошибок SQL, транзакционных гонок, открытого карантина и потери результата; настоящий `pg_dump -Fc`/`pg_restore` PostgreSQL 17, повторные SQL-сессии с отказом при replay, независимый второй CI-runner без DB/AWS, который повторно вычисляет исходный bundle SHA и **проверяет обе подписи** на переданном не-секретном отчёте.

## Достоверность и запреты

В CI настоящий disposable PostgreSQL 17; внешние AWS, S3, GitHub environment approval history и личности людей `не подтверждены`. Исходные проверки провайдеров R179 используют синтетические ответы. Нельзя считать два временных ключа двумя разными проверяющими. Доступ текущего GitHub connector недостаточен для чтения защиты ветки и настроек environment, поэтому реальная конфигурация не объявляется проверенной.

`productionAuthorized=false`. Ни `main`, ни публичный сайт, реальные платежи/данные, ни AWS/STAGING не изменяются.

Техническая приёмка только после SUCCESS обоих jobs R180 на точном SHA последнего коммита.
