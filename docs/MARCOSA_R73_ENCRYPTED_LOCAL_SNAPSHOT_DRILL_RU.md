# MARCOSA R73 — шифрованный автономный архив SQLite и испытание восстановления

**Действует только для локальной лаборатории Node 22 / SQLite.** Не является системой PostgreSQL PITR, полноценным offsite-бэкапом, графиком восстановления или гарантом RTO/RPO. Включение в GitHub `main` не публикует личные данные.

## Зачем

R67 сохраняет согласованную резервную копию локальной SQLite, но файл на диске не зашифрован. R73 добавляет отдельную исполняемую утилиту `ops/encrypted-local-archive.mjs` для упаковки **уже проверенного R67-снимка** и его манифеста в единый аутентифицированный архив.

## Команды оператора

Подготовить защищённый файл с секретной фразой длиной не менее 24 байт (в примере генерация локальным криптографически случайным источником):

```sh
mkdir -p private
umask 077
openssl rand -base64 48 > private/backup-passphrase
chmod 600 private/backup-passphrase

node ops/local-backup-restore.mjs backup \
  --db private/local.sqlite \
  --out private/snapshot.sqlite

node ops/encrypted-local-archive.mjs seal \
  --db private/snapshot.sqlite \
  --manifest private/snapshot.sqlite.json \
  --out private/snapshot.marc \
  --passphrase-file private/backup-passphrase

node ops/encrypted-local-archive.mjs unseal \
  --archive private/snapshot.marc \
  --out private/restore-test.sqlite \
  --passphrase-file private/backup-passphrase
```

Файл фразы **не включать** в архив, GitHub, issue, чат, системный лог или место хранения encrypted archive. Ключ следует безопасно передать иному доверенному хранителю или в утверждённый менеджер секретов; без него архив невозможно восстановить. Операция `unseal` создаёт **новую базу**, никогда не перезаписывает оригинальную.

**Важно:** после успешного шифрования исходные `snapshot.sqlite` и `snapshot.sqlite.json` **по-прежнему лежат открытым текстом**. Утилита намеренно не удаляет их без участия оператора. Перед внешним переносом хранить исходные файлы только в закрытой папке и очищать по утверждённой процедуре хранения. Архивировать в GitHub Actions настоящие приватные пользовательские БД запрещено.

## Формат безопасности

- AES-256-GCM со случайным nonce 96 бит и солью 128 бит для **каждой** операции; парольная фраза переводится в AES-ключ через `scrypt N=32768, r=8, p=1`.
- Содержимое архива: открытый короткий version header/salt/nonce, затем **зашифрованные манифест и полный SQLite**, и 16-байтный GCM authentication tag. Почта, названия миров, жалобы и встроенные PNG не попадают в незашифрованные метаданные или stdout.
- Перед seal подтверждаются `PRAGMA integrity_check`, отсутствие FK-нарушений, размер и SHA-256 текущего локального R67-снимка.
- `unseal` сверяет GCM tag, зашифрованный манифест, SHA-256, размер и целостность SQLite. До полного успешного завершения результат существует только во временном файле `0600`; публикация выполняется атомарным create-only hardlink. Неверный пароль, модификация тега, подмена байтов, симлинк или уже существующая цель приводят к отказу и очистке незавершённого результата.
- Пароль не принимается через CLI-флаг с plaintext или через stdout: только локальный обычный файл с закрытыми правами владельца `0600`.

## Исполняемая проверка

`node --test ops/test/encrypted-local-archive.test.mjs` создаёт отдельный реальный Node/SQLite сервер и тестовый профиль с пользователями, PNG, жалобой на изображение и согласиями беты. Затем R67 snapshot → R73 seal → R73 unseal → вновь открываемая MARCOSA на восстановленной базе. Проверяются отдельный соль/nonce на двух архивах, отсутствие plaintext в архиве, совпадение каждого BLOB и таблиц, SHA, права `0600`, CLI, неверный пароль, tampered ciphertext/tag, symlink и отсутствие перезаписи. CI добавлен к обязательной проверке R49 local load. Это **настоящая проверка**, не имитация API резервного копирования.

## Открытые production-блокеры

Реальная мировая эксплуатация требует отдельного Supabase project, согласованного бэкапа PostgreSQL + Private Storage, расписания, offsite региона, контролируемого KMS и ротации ключей, проверенного восстановления в отдельном окружении, независимой DR-приёмки и законной процедуры удаления/удержания. Отдельные файлы SQLite R67/R73 не доказывают работоспособность Postgres/S3/мультисервера. Глобальный gate #55 остаётся **BLOCKED**.
