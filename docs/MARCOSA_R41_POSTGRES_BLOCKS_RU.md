# MARCOSA R41 — PostgreSQL-доступ к блокировкам пользователей

Это **настоящий запускаемый SQL-контракт** для автономного PostgreSQL 17 в GitHub Actions, но не миграция в production Supabase.

## Фактическая реализация

- Новая `public.marcosa_user_blocks` связывает blocker/blocked по UUID из `auth.users`; физический FK каскадно удаляет блокировку после удаления одного из аккаунтов.
- Включён RLS. Только роль `authenticated` с `blocker_id = auth.uid()` получает право SELECT своих строк. Анонимные не получают SELECT; один пользователь не может прочитать, кто заблокирован другим.
- Клиентам **не выдаются INSERT/UPDATE/DELETE**: изменение блокировки должно выполняться доверенным backend-транзакционным сервисом, который одновременно удалит mutual follows и старые уведомления и отзовёт рекламное согласие. Прямая запись через Data API запрещена.
- Композитные индексы покрывают поиск блокировок по владельцу и по адресату, CHECK запрещает self-block, уникальный ключ запрещает дубли.
- `tests/postgres/30_rls_user_blocks.sql` запускается в GitHub CI с Alice/Bob/Carol и реально доказывает изоляцию, отсутствие клиентских прав на запись, запрет анонимного чтения, self-block и дубликатов.

## Проверка и нерешённые зависимости

Изолированный CI запускает последовательно R30, R37 и R41 SQL. Только проход этого теста позволяет объединить PR.

Для реального глобального запуска *не достаточно* этой схемы: нужно подключение проверенного Supabase проекта, Auth/JWT, отдельный backend для атомарных социальных операций, RLS-изоляция источников данных и независимый security audit. Подключённый Supabase в этом рабочем пространстве пока не показывает проектов. Никакой production SQL или секреты здесь не используются.

Помни: блокировки регулируют общение между авторизованными людьми, а не приватность уже опубликованных публичных Worlds. Не нужно обещать заблокированному человеку техническую невозможность открыть общедоступную страницу без входа.
