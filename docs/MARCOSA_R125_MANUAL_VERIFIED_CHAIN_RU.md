# MARCOSA R125 — управляемые серверные аудиты вместо каскада GitHub Actions

Дата: 2026-10-26. Статус: проверка безопасности CI. **Production NO-GO.**

## Причина изменения

GitHub запускает `workflow_run` после завершения всего workflow, даже когда критический job был `skipped`, а общий вывод `success` относится только к offline-тестам. Автоматическое R117 → R118 → R119/R120/R121 создавало много ненужных проверок на одном SHA, некоторые отменялись до выполнения. R124 защищает настоящие доказательства, но его уникальные concurrency-группы без смены триггеров могут сохранять лишнюю очередь.

## Операторский порядок

1. R116 остаётся связанным с завершением настоящего STAGING. Подтвердить `read-only-vps-proof=success` и действительный R116 artifact с текущим SHA. Старый R116 без этого артефакта не годится.
2. Запустить R117 вручную `workflow_dispatch` на **main**. Обязателен доказанный Pages HTTPS, STAGING и настоящий R116. PR-события R117 дают только offline-тесты.
3. Запустить R118 вручную `workflow_dispatch` на **main**. Прежде чем вызывать pinned non-root read-only SSH-аудит, R118 заново вычисляет R117 сертификат по тому же SHA. Для годного результата нужны оба завершённых job и nonexpired R118 NO_GO artifact.
4. R119/R120/R121 теперь автоматически продолжают только R118, запущенный **вручную на main**. Они независимо требуют `live-production-parity=success`, правильный точный SHA и реальный R118 NO_GO artifact; общий зелёный статус не заменяет серверную проверку.
5. Для R122 получить два независимых снимка: дважды вручную запустить R118 на одном актуальном SHA, дождаться двух отдельных R121 `actual-vps-public-hashes=success` с разными run ID и артефактами. Запустить R122 вручную с парой R121 ID и проверить полное совпадение SHA-256 каждого публичного файла.

Это не непрерывный мониторинг: оператор вручную создаёт две независимые проверяемые цепочки только тогда, когда STAGING и внешние зависимости действительно готовы. Старые артефакты другого SHA не использовать.

## Границы

R125 не меняет ни одного production-файла `marcosa.club`, SQL, Nginx/DNS, авторизацию или пользовательские данные. Запросы SSH остаются read-only; отдельный R119 использует временную лабораторию, не production. R122 не разрешает выпуск.

Слияние R124 необходимо как базовый security gate; затем требуется собственная CI-приёмка R125 и независимый ручной прогон серверного контура. Существующие R48, Chromium и юридический/security release gate остаются обязательными. Нужны отдельные доказательства legacy compatibility, Auth/RLS, восстановления PostgreSQL+Storage и подтверждённое human GO. Пока **NO-GO**.
