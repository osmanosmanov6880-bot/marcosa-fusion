# MARCOSA R11 — резервная копия с паролем

**Дата: 24 октября 2026.** Результат относится к публичному статическому демонстрационному Creator Engine. Публикация на GitHub Pages возможна только после зелёных CI-проверок. Настоящий аккаунт, облачная синхронизация и серверная модерация не добавлены.

## 1. Новая функция

В Creator Engine, под обычным разделом «Резервная копия архива», появляется отдельная панель **«ЗАЩИЩЁННЫЙ АРХИВ»**:

1. Пользователь вручную сохраняет истории и версии в локальном архиве R9.
2. В поле «Пароль архива» вводит новую уникальную парольную фразу, длиной не менее 12 и не более 256 символов. Рекомендуется несколько случайных слов, не пароль от основной учётной записи.
3. Для создания файла повторяет пароль в отдельном поле, затем нажимает «Скачать зашифрованный архив».
4. Файл с расширением JSON содержит версию алгоритма, параметры создания ключа, случайную соль, nonce и **зашифрованный текст** всех проектов со всеми версиями.
5. Для восстановления вводит тот же пароль (повторное поле при импорте не требуется), выбирает зашифрованный JSON и подтверждает объединение проектов. Записи сохраняются по тем же правилам R10: одинаковые истории пропускаются, расходящиеся копии получают новые идентификаторы, существующая история не перезаписывается.
6. После успешной или неуспешной операции поля пароля очищаются. Никакого пароля не записывается в IndexedDB или localStorage и не отправляется на сервер.

**При забытом пароле восстановление невозможно.** Ни служба поддержки, ни ChatGPT не могут извлечь ключ из зашифрованного файла. Встроенной проверки сложности, кроме длины/управляющих символов, нет: слабые угадываемые пароли уязвимы к перебору офлайн.

## 2. Криптографический формат

- Envelope schema: marcosa-encrypted-vault/v1.
- Шифрование: **AES-256-GCM**, тег аутентификации 128 бит.
- Производный ключ: **PBKDF2-HMAC-SHA-256**, ровно **600 000** итераций. PBKDF2 замедляет перебор, но не обладает память-затратными свойствами Argon2id. Для критичных секретов используйте специализированный инструмент защищённого хранения файлов.
- Случайная соль 16 байт и nonce 12 байт создаются **с помощью crypto.getRandomValues** при каждой выгрузке.
- Additional authenticated data: MARCOSA:encrypted-vault:v1.
- Пакет предварительно проверяется строгим валидатором R10, размер чистого JSON до 2 МиБ. Размер encrypted envelope ограничен примерно 2.8 МиБ.
- При расшифровке результат проходит тот же строгий R10/R9 валидатор полей/версий. Не принимаются импортируемые флаги реального одобрения модератором.
- Отклоняются неизвестные поля envelope, подмена алгоритма, уменьшение числа итераций, некорректный Base64 и повреждённый UTF-8.

**Это защита выгруженного файла, не шифрование браузерной базы.** IndexedDB по-прежнему хранит авторский текст в доступном для браузера виде. Старый экспорт R10 **без шифрования** также остаётся доступным.

## 3. Границы и приватность

- Все операции выполняются локально через WebCrypto (crypto.subtle) на HTTPS или localhost.
- Никаких сетевых запросов с авторским содержимым, облачной загрузки, паролей в URL, аналитики или оплаты в R11 нет.
- Файл сохраняется штатным механизмом загрузки браузера. Приложение не удерживает пароль в собственной постоянной базе; в процессе операции текст и пароль временно присутствуют в оперативной памяти.
- Изначальные файлы и версии R9/R10 не перезаписываются. Если нет свободного места из лимита 8 проектов, восстановление отменяется целиком.

## 4. Приёмка

- tests/crypto.test.cjs: настоящий WebCrypto в Node 22 — AES-GCM roundtrip, UTF-8, свежие соль/nonce, неправильный пароль, изменённые ciphertext/salt/nonce, неизвестные поля, ограничения и отсутствие plaintext в envelope.
- tools/r9_cdp_smoke.cjs: Chromium desktop/mobile и настоящая IndexedDB. Проверка зашифрованного экспорта из UI, правильного пароля, отклонения подделанного файла, восстановления после удаления, повторного импорта без дубликатов, неправильного пароля, очистки полей ввода.
- tools/r5_capture_preview.py: изображения криптографического раздела на компьютере и телефоне.
- Статическая сборка: **14** публичных файлов в allowlist с SHA-256 manifest. В деплой не попадают исходные SQL-проекты, секреты или содержимое пользовательских копий.

## 5. Что НЕ сделано

- Нет аутентификации Supabase, облачной базы, центральной модерации, API публикации или монетизации.
- Подключение Supabase на момент проверки 24.10.2026 показывает пустой список проектов. R10 SQL существует **только как неисполненный проект схемы**.
- Contabo SSH-проблема не решена; staging останавливается при несовпадении ключа сервера.

Для последующего серверного выпуска понадобится доступный проект Supabase, проверка RLS на разных реальных учётных записях и самостоятельная настройка политик приватности. Шифрование локального экспорта не заменяет эти процессы.
