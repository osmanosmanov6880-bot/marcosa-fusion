# MARCOSA R105 — безопасный монтаж нового раздела без замены старой платформы

## Область действия

**Производственная платформа не заменяется.** Предлагается добавить только `/network-os/` на существующий HTTPS-домен `marcosa.club`. Это отдельный статический предпросмотр 62 активов; действующие `/`, `/api`, личные страницы, Supabase и пользовательские данные остаются в прежнем приложении.

Исходная проверка R104 (GitHub run #40234582480): Nginx HTTPS active, `/opt/marcosa/current` принадлежит root, предыдущий индекс неизменён, маршрут `/network-os/` не занят. Ключ `DEPLOY_SSH_KEY` относится к непривилегированному `marcosa-deploy` и **не может** изменять Nginx.

## Созданные артефакты

- `ops/install_production_canary.py`: **root-only** установщик с режимами `plan`, `apply`, `rollback`.
- `tests/test_canary_install.py`: тесты консервативного поиска целевого server-блока, исключения конфликтов, отказа при изменении манифеста и защита исходного сайта.
- `.github/workflows/marcosa-r105-canary-package.yml`: автономные тесты; **никакой root-установки из Actions**.
- `ops/production_canary_readiness.py`: в следующем R104 read-only отчёте также выдаётся контрольная сумма актуального Nginx site-файла, чтобы установщик отказал при любом изменении конфигурации после предварительной проверки.

## Какие условия проверяет установщик

1. Запуск только на `vmi3625032` и с явным подтверждением root-администратора.
2. Исходная конфигурация Nginx точно совпадает с независимо полученным SHA-256.
3. Наличие **одного** подходящего HTTPS server-блока, соответствующего `marcosa.club` и `/opt/marcosa/current`.
4. Никакого существующего `/network-os/` или активного аналогичного include.
5. Сравнение каждого публичного файла STAGING с проверенным manifest; запрет `.env`, ссылок, обхода каталогов и особых файлов.
6. Создание выделенного `/var/www/marcosa-network-os/` для новых ресурсов, не в `/opt/marcosa/current`. Читаемый Nginx каталог и отдельно ограниченные доступы публикации.
7. Резервное копирование site-конфигурации Nginx под root и использование отдельного `include`; затем `nginx -t`, `systemctl reload nginx` и HTTPS-readback точного `index.html`.
8. При сбое — восстановить сохранённую site-конфигурацию и перезагрузить Nginx. При ручном `rollback` новый маршрут удаляется, но исходный сайт остаётся целым.

## Почему это не запущено автоматически

Ручное действие администратора **обязательно**: аккаунту CI нельзя давать root-доступ или отключать SSH-проверку для размещения нового раздела. Текущие действия GitHub могут полностью проверять и публиковать STAGING, но не имеют прав на запись `/etc/nginx/` и `/opt/marcosa/current`.

После успешной установки нового раздела потребуется отдельное разрешение на автоматическое обновление выделенного sidecar. До этого новый Nginx route будет указывать на изолированную копию одного проверенного релиза, без влияния на основной сервис.

Важно: эта процедура не является миграцией старых учётных записей, базы данных, приватных сообщений и платежей. Статический предпросмотр не получает их ключи или доступ.
