# MARCOSA — мировой продукт: окончательный план исполнения крупными блоками

**Контрольная дата:** 25 октября 2026. **Источник истины:** GitHub `osmanosmanov6880-bot/marcosa-fusion`. **Релизный gate:** [Issue #55](https://github.com/osmanosmanov6880-bot/marcosa-fusion/issues/55). Этот документ разделяет код, CI, реальную инфраструктуру, спрос и коммерцию.

## Нулевой факт: что уже реально создано

Существуют **две разные поставки**:
1. публичный статический **Network OS Preview** (не исполняет социальные API, не хранит реальные профили и не принимает платежи);
2. настоящий исполняемый **Node 22 + SQLite social lab** в `server-lab/`, защищённый loopback Host/Origin, HttpOnly сессиями и проверками пользователей.

Второй слой включает реальные локальные механизмы: регистрация и одноразовые приглашения, Worlds, публикации и черновики, комментарии, подписки, поиск, личные уведомления, настройки уведомлений, блокировки, сохранения, модерация и апелляции, согласование *неоплаченных* рекламных заявок, мировую редакционную таксономию, статистику автора и закрытой беты, экспорт/удаление и офлайн backup/restore. Интегрированные этапы R30–R52 прошли соответствующие тесты GitHub. Отдельные PostgreSQL reference-RLS SQL контракты R30/R37/R41/R43/R46/R51 протестированы в disposable CI, но **не применены к настоящему Supabase**.

На 25 октября подключённый Supabase возвращает `projects: []`. Последний изолированный STAGING не развёрнут: независимая проверка закреплённого SSH host key не совпала с наблюдаемым ключом. Публичная социальная Auth, реальная оплаченная реклама, пользователи и продуктово-рыночное соответствие **не подтверждены**.

## Блок A — инфраструктура, собственность и доверенный STAGING

**Что сделать:**
- установить документированного ответственного за сервер, домен, репозиторий, резервные копии и Supabase;
- через консоль владельца сервера независимо получить подлинный публичный SSH host key и объяснить ротацию; обновить pin только после проверки;
- создать изолированный HTTPS STAGING, без доступа к production user-data, минимально привилегированный deploy, отдельные ключи и секреты;
- настроить на каждый коммит сборку, smoke, rollback, backup и проверяемое восстановление.

**Приёмка:** реальный staging URL и TLS, host fingerprint подтверждён независимым источником, CI показывает удачную проверку identity, documented SSH pin, успешный deploy и rollback. До этого **BLOCKED**. Никогда не использовать `StrictHostKeyChecking=no` и не принимать `ssh-keyscan` как самостоятельную верификацию.

## Блок B — настоящая PostgreSQL/Auth многопользовательская основа

**Что сделать:**
- подключить существующий проект/организацию Supabase через законного владельца, без создания нового платного проекта без согласия;
- обследовать Postgres/Auth/Data API, выполнить безопасную инвентаризацию схем, отдельную staging database/branch, backup и rollback;
- преобразовать справочные SQL R30/R37/R41/R43/R46/R51 в проверенные миграции настоящего приложения, устранив расхождения моделей с SQLite;
- подключить Auth: verified email, восстановление, MFA модераторов, real JWT и session revocation; пользовательская `raw_user_meta_data` не является полномочием;
- реализовать доверенный backend для записи событий, блокировок, приватных данных, приглашений, модерации и рекламных решений; не помещать `service_role` в браузер.

**Приёмка:** два независимых настоящих staging JWT + анонимный посетитель + модератор; позитивные и негативные тесты для каждого типа записи; guest/public/private границы, удаление/экспорт, MFA и восстановление, FK, аудит schema grants и Security Advisor. Настоящий backup/restore обязателен. Пока отсутствует доступный Supabase проект — **BLOCKED**.

## Блок C — полноценный защищённый продукт и медиа

**Что сделать:**
- рабочие публичные профили/Worlds с редакционными категориями, поиском, реальными прямыми ссылками, черновиками и приватностью;
- загрузка фото и видео через разрешённые MIME, размер, квоты, content sniffing, безопасную обработку и signed URLs; политики Storage buckets;
- жалобы, очередь модерации, независимые апелляции, блокировки, история согласий, антиспам, безопасное обращение с недопустимым контентом;
- доступный premium UI (без излишней футуристичности): RU/EN, адаптивные экраны, клавиатура и экранные считыватели, WCAG 2.2 AA, SEO/OG, LCP/INP и реальная мобильная QA.

**Приёмка:** приглашённый человек подтверждает почту → создаёт World → загружает законное медиа → публикует → получает подписку/комментарий → блокирует/жалуется → апеллирует → экспортирует/удаляет данные; всё на настоящем STAGING, с минимум двумя независимыми аккаунтами и замерами на телефонах. Не считать картинку в GitHub Pages завершением этого блока.

## Блок D — честная рекламная система и платежи

**Что сделать:**
- юридическая верификация рекламодателя, заявка, права на использование бренда, согласие владельца World, независимая проверка и отзыв согласия;
- отдельные server-side campaign/placement/receipt события только от реально исполненной доставки, антифрод и аудит; явно маркировать рекламные публикации;
- тарифы после интервью с реальными покупателями, договоры, биллинг, верифицируемые подписанные webhook события, возвраты, налоги, квитанции, баланс и ledger;
- разграничить тестовые «одобренные заявки», **фактические показы**, **подтверждённые оплаты** и **выручку после возвратов**.

**Приёмка:** юридические документы, реальный платёж в тестовой/разрешённой среде провайдера, проверка повторной доставки webhooks, отзыв и остановка кампании, честные панели с источниками данных. Пока нет этих доказательств: `paidRevenue=null`, `verifiedImpressions=null`, коммерческий выпуск **BLOCKED**.

## Блок E — закрытая бета и экономика удержания

**Что сделать:**
- 10+ качественных интервью с авторами и 10+ независимых интервью с потенциальными рекламодателями, протоколы с согласиями;
- 10 независимых usability-тестов без подсказок, потом когорта до 100 добровольно приглашённых авторов; регистрировать точный знаменатель каждой воронки;
- измерять создание первого World, first publish, useful reply, возвращение D7/D30, активные авторские сообщества, жалобы, отказы, реальные заявки рекламодателей;
- считать CAC/активацию, retention и честную конверсию пилотной рекламы после создания законного измерительного слоя, избегая самообмана тестовыми событиями.

**Приёмка:** датированные когортные отчёты и независимая оценка продления/покупки рекламодателями. Пока нет реальных данных — отсутствие данных обозначается **неизмерено**, не нулём и не успехом.

## Блок F — безопасность, нагрузка и операционный масштаб

**Что сделать:**
- production incident response, углублённый dependency/security audit, ограничения злоупотреблений, защищённые секреты и ротацию ключей;
- настоящие SLO/error budgets, observability и оповещение, повторяемый тест восстановления, load тесты STAGING/edge с согласованным профилем и отказами;
- проверить p95/p99 с пользовательскими размерами данных, работу при частичных отказах и откат Canary; отдельно тестировать медиа и очереди;
- пройти независимую приватностную, юридическую и доступностную экспертизу для выбранных юрисдикций перед выходом на другие рынки.

**Приёмка:** внешний технический акт, заведомо ограниченный canary, рабочий rollback и incident drill, подписанный владелец релиза. Локальный R49 тест на 480 запросах — только лабораторная база, **не** глобальная нагрузочная гарантия.

## Блок G — международный go/no-go и выпуск

Проверять `ops/check-release-gate.mjs` для staging, beta, public. Даже если ссылки на доказательства валидны, программа возвращает максимум `READY_FOR_INDEPENDENT_REVIEW`: она не аутентифицирует независимого проверяющего и **никогда** не разрешает сама себе production-деплой. Обязателен человеческий sign-off владельца, безопасности, юридической ответственности и эксплуатации.

**Порядок:** A → B → C → закрытая E → D после правовой/платёжной проверки → F → G. Коммерческая функциональность может проектироваться параллельно, но запускать оплаченные кампании до нужных gate нельзя.

## Минимальный список проверок настоящего запуска

- [ ] Supabase проект владельца доступен и проверен; миграции применены к согласованной staging-ветке с backup/rollback.
- [ ] Подлинность SSH ключа подтверждена из панели хостинг-провайдера; HTTPS STAGING опубликован и изолирован.
- [ ] Реальный Auth/JWT/RLS, восстановление почты и MFA модератора прошли независимые тесты.
- [ ] Медиа/модерация/экспорт/удаление имеют явные права, лицензии и защиту злоупотреблений.
- [ ] Платежи, рекламная статистика, возвраты и договоры реально проверены (для коммерческого публичного запуска).
- [ ] Есть реальные согласившиеся пользователи, верифицированные когорты, сценарии поддержки и реагирования.
- [ ] Нагрузочный, security, accessibility, restore и rollback gate закрыты на реальной инфраструктуре.
- [ ] Независимый go/no-go подписан владельцем. До этого публичную MARCOSA нельзя объявлять завершённой.

**Зависимость, которую код не заменит:** владелец должен предоставить доступ к собственной инфраструктуре и подтвердить её подлинность. Не передавать пароли, private SSH keys, `service_role`, seed-фразы или пользовательские базы в переписку. Полный журнал доказательств и блокировок — Issue #55.
