# MARCOSA R126 — отдельный R118-источник для каждой независимой инвентаризации

Дата: 2026-10-26. Статус: Draft security release, production **NO-GO**.

## Проблема

R122 прежде проверял два разных R121 workflow run ID, два настоящих `actual-vps-public-hashes` job и два отдельных артефакта. Однако эти результаты могли происходить из **одного и того же upstream R118**. Это слабее требования двух независимых цепочек проверок.

## Изменение

1. Только реальный серверный шаг R121 получает `R118_RUN_ID` из доверенного контекста GitHub Actions `github.event.workflow_run.id`. Предыдущий шаг проверяет тот же source ID модулем `ops/r123_upstream_live_gate.mjs` до обращения к SSH.
2. `ops/r121_full_public_inventory.mjs` теперь отвергает отсутствующий/нецелый/неположительный `R118_RUN_ID`, записывает `r118UpstreamRunId` в ограниченный JSON-отчёт и по-прежнему заявляет только публичный read-only baseline и `NO_GO`.
3. `ops/r122_dual_vps_inventory_gate.mjs` требует присутствия этого поля в обоих реально проверенных R121 артефактах и **разные** upstream R118 run ID. Повтор одного R118 с двумя R121 job больше не даёт PASS.
4. Старый артефакт R121 без поля R126 больше не подходит для нового R122. Выдавать ему задним числом «PASS» нельзя; нужны новые два VPS-снимка после обновления кода.
5. Регрессионные тесты проверяют отсутствие R118 ID, неподходящие значения, две R121 записи из одного R118 и неизменность `productionCutoverAuthorized=false`.

## Строгая граница доказательства

R122 подтверждает разные **сообщённые из доверенного R121 workflow** R118-идентификаторы, но **не делает отдельный вызов GitHub API к исходным R118**. Поэтому поле `r118UpstreamEventIdentityIndependentlyProven` остаётся `false`; это не криптографическая аттестация происхождения и не согласие на migration. Для каждого R121 GitHub Actions ещё до SSH выполняет R123-проверку реального R118 VPS job и NO_GO artifact.

Никаких изменений production `marcosa.club`, Nginx, DNS, Auth, PostgreSQL, Storage, аккаунтов или пользовательских данных. Ручное проведение полного сценария должно следовать R125: актуальные STAGING и Pages → реальный R116/R117 → два отдельных R118 → два настоящих R121 → R122. Реальные Auth/RLS, backup/restore и release approval остаются NO-GO.
