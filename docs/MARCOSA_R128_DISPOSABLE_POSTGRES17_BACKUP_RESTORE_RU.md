# MARCOSA R128 — реальное dump/restore на изолированной PostgreSQL 17

## Что теперь проверяет CI

После всего уже существующего R30–R84 PostgreSQL/RLS тестового сценария отдельный
job step создаёт **настоящий архив pg_dump -Fc** синтетической базы в одноразовом
PostgreSQL 17 Docker-контейнере. Используется pg_dump той же версии 17,
без внешних адресов и без реальных пользователей.

После R30–R84 тестов дополнительно создаются две новые одноразовые Auth-фикстуры с приватным и публичным World/постом. Сохраняются агрегированные счётчики исходных таблиц и сравниваются с новой базой.

Затем создаётся **новая** база `marcosa_r128_restored` из `template0`,
и с `pg_restore --exit-on-error --no-owner` восстанавливаются таблицы,
функции, политики RLS, права GRANT, внешние ключи и синтетические записи.
`--no-acl` намеренно НЕ используется: иначе можно незаметно потерять права.
В SQL `tests/postgres/130_pg17_restore_rls_isolation.sql` повторно проверяются
эти новые записи из фикстур, защита закрытого sponsor ledger и различия доступа для
`anon`, Bob и Alice, включая private world и private post.
Испорченный архив отклоняется. Создаётся только очищенный JSON-доказательный
артефакт GitHub Actions; сам архив и синтетическая база не сохраняются.

## Чего R128 НЕ доказывает

Это проверка одноразовой модели **внутри CI**, а не настоящий backup+restore
текущего Supabase проекта, не PITR, не backup файлов Storage, не проверка
настоящих JWT и не восстановление существующих учётных записей. Глобальные роли
созданы только фикстурой тестовой инфраструктуры. Реальный production доступ,
данные пользователей, DNS и Nginx не используются. Старый `marcosa.club` остаётся
на месте, release status **NO_GO**.

Для настоящего GO по-прежнему необходимы владелец действующей Supabase/PG/Storage
инфраструктуры, изолированный test restore её резервной копии, проверка
Auth/RLS/Storage с реальными staging JWT двух пользователей и доказанная
совместимость пяти legacy интеграций. Ни один успешный синтетический CI не
заменяет эту процедуру.
