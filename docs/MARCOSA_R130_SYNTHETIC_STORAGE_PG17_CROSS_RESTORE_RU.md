# MARCOSA R130 — синтетический Storage + PostgreSQL 17: восстановление и проверка байтов

Дата: 26 октября 2026. **Production NO-GO.** Это инженерная проверка восстановимости двух фиктивных объектов и связанных записей базы **в GitHub Actions**, а не миграция реального Supabase Storage.

## Что проверяется в одном disposable CI job

1. Node.js 22 создаёт **два настоящих RGBA PNG** размером 64 × 48 пикселей. Файлы сохраняются под проверяемыми SHA-256 именами: `world-covers/<world UUID>/<sha256>.png`. Данные детерминированы, не содержат реальных фотографий пользователей.
2. Перед `pg_dump -Fc` R128 добавляет в одноразовый PostgreSQL 17 два `world_cover_assets`: закрытый World пользователя Alice остаётся `pending`, публичный World Bob получает `approved` только с **третьим независимым проверяющим**. Проверяются триггеры совпадения владельца, пути и SHA-256.
3. R128 делает **настоящий** SQL dump и restore в новую `marcosa_r128_restored`; R128 повторно проверяет приватные World/post и GRANT/RLS.
4. R130 независимо копирует исходные PNG в закрытый каталог резервной копии. В `manifest.json` хранится отсортированный список ключей, SHA-256, байтов и PNG-размеров; SHA-256 всей канонической ведомости фиксирует состав. Архивные каталоги не заменяют существующие.
5. Затем файлы копируются в **новую**, не существовавшую ранее папку восстановления и повторно проверяются побайтно. Отклоняются изменённые PNG, плохие CRC, повреждённые/дополнительные записи, символические ссылки, неверные объекты и подмена Storage пути.
6. Действительно восстановленная PostgreSQL 17 отдельно проверяется SQL `tests/postgres/131_r130_restored_storage_acl.sql`: сохранность приватной RLS-схемы, отсутствие доступа `anon` и `authenticated` к частным Storage ключам, запрет владельцу менять статус модерации, приватность Alice и независимый reviewer Bob.
7. R130 читает **две реальные восстановленные SQL-записи**, а не подставляет фиктивный JSON: сверяет `storage_key`, `sha256`, `byte_size`, `width/height`, владельца World, видимость, статус и `reviewed_by` с восстановленными физическими PNG-файлами.
8. GitHub сохраняет только `marcosa-r130-disposable-storage-restore-proof.json` — краткий очищенный отчет **без двоичных объектов**, без SQL dump, токенов или реальных данных. Все временные файлы и тестовая база удаляются самим runner/container после job.

## Границы и последствия

- Используется **локальная папка**, имитирующая Storage; это не Supabase Storage API, не S3/MinIO backup/restore, не пользовательские аватары и не действующие объекты из `marcosa.club`.
- SQL использует симуляцию ролей и `request.jwt.claim.sub` в PostgreSQL, а не настоящие выпущенные Supabase JWT/сессии.
- SHA-256 фиксирует содержимое и ошибку копирования, но **не доказывает подлинность без доверенного исходного ключа или подписанного контрольного манифеста**; source fixture полностью синтетический.
- Не подтверждены PITR, шифрование offsite, доступность оригинального Auth проекта, подписанные URL и Storage RLS реального сервиса, восстановление настоящих объектов и удаление аккаунтов.
- Production, DNS, Nginx, `/opt/marcosa/current`, OAuth, PostgreSQL/Storage клиентов и данные пользователей **не изменяются**. До полного независимого восстановления реальной базы и Storage, compatibility issue #135, отдельного владельческого допуска и ручного R117 → 2 × R118 → 2 × R121 → R122/R127 статус **NO-GO**.

## Где код

- `ops/r130_disposable_storage_restore.mjs` — создание PNG, проверка CRC, резервная копия, восстановление и сверка записей PostgreSQL.
- `tests/r130_disposable_storage_restore.test.mjs` — unit / negative checks на целостность, подмену, доступ и безопасный отказ.
- `tests/postgres/131_r130_restored_storage_acl.sql` — реальные проверки восстановленной PostgreSQL 17.
- `.github/workflows/marcosa-postgres-rls-reference.yml` — один связанный без production-секретов сценарий R128 + R130.
