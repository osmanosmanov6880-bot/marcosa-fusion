# MARCOSA R124 — фактический VPS-job обязателен и для R120/R121

## Причина

R123 исправил ложноположительный статус R119: GitHub Actions может вернуть общий `success` после успешных offline-тестов, даже когда проверка `live-production-parity` (R118) была `skipped`.

R120 (контроль публичного индекса, числа файлов и пяти обязательных модулей) и R121 (полная инвентаризация SHA-256 публичных файлов) всё ещё ориентировались на общий `workflow_run.conclusion == success`. Наличие JSON-файла из того же GitHub run уже было обязательным, но конкретный успешный VPS-job не аттестовывался явно.

## Дополнительная подтверждённая причина отмен

Ряд R118 `workflow_run` на одном SHA завершился `cancelled` без единого созданного job. При `concurrency.group` только по SHA GitHub Actions может вытеснить старый **pending** run более новым pending run, даже если `cancel-in-progress: false`. Это не ошибка Node или приложения.

R124 присваивает уникальную concurrency-группу по **ID конкретного upstream workflow_run** для всей цепочки R116, R117, R118, R119, R120 и R121. Ручные/PR-запуски используют собственный `github.run_id`. Однотипные источники не выдавливают друг друга из очереди только потому, что имеют одинаковый SHA. Это может увеличить число отдельных read-only проверок при многочисленных upstream-событиях, но сохраняет независимые свидетельства.

## Дополнительный критический дефект R116 / R117

В [R116 run 40249776942](https://github.com/osmanosmanov6880-bot/marcosa-fusion/actions/runs/40249776942) GitHub показывал `read-only-vps-proof=success`, но фактический job log закончился `R116_PREVIOUS_RUN_SUPERSEDED=SKIP` и **никакого SSH-вызова не было**. В том workflow на несовпадение `git rev-parse HEAD` и `EXPECTED_SHA` стоял `exit 0`. Это недопустимое ложное доказательство, даже если GitHub выставил весь запуск зелёным.

R124 исправляет отказ на `exit 2`, а R116 при фактическом успешном read-only SSH и проверке старого релиза выпускает отдельный ограниченный `marcosa-r116-actual-vps-rollback-proof` artifact только после прохождения всех строк `STAGING_ROLLBACK_PREFLIGHT=PASS`, SHA текущего релиза, SHA-256 всех файлов отката и `PRODUCTION_UNCHANGED=YES`.

R117 проверяет, что **этот** конкретный R116 run имеет завершённый job `read-only-vps-proof=success` **и** ровно один ещё не истёкший `marcosa-r116-actual-vps-rollback-proof` artifact с привязкой к тому же run ID. Отсутствие artifact — `FAIL`, не `PASS`. Это аттестация происхождения артефакта из защищённого GitHub workflow; его наличие не доказывает миграцию Auth, Storage, Postgres или production. Для более строгой проверки содержания самого JSON можно дополнительно выполнять загрузку и сверку SHA при выпуске сертификата.

Повторно проверены негативные условия тестами R117 и R124. Старые зелёные R116 без такого artifact **не считаются** настоящим PASS.

## Новый защищённый порядок

1. После завершения R118 запускаются независимые R120 и R121; на каждый **конкретный upstream GitHub run ID** создаётся своя группа concurrency. Это важно, когда в одном коммите два запуска R118: pending-задания не вытесняют друг друга только из-за одинакового SHA.
2. Требуются полный 40-символьный исходный SHA и соответствие `git rev-parse HEAD`. Старый или другой коммит блокируется.
3. Через `gh api` читаются реальные метаданные конкретного R118 запуска, оба jobs (`offline-contract`, `live-production-parity`) и связанный non-expired artifact. Воспользоваться «общим зелёным workflow» со `skipped` живым job больше невозможно.
4. Скачивается только ограниченный по размеру `marcosa-r118-production-boundary-no-go`. Оба downstream вызывают уже проверенный модуль `ops/r123_upstream_live_gate.mjs`, который проверяет реальную задачу, источник SHA и все запреты production (`NO_GO`).
5. **R120** после подтверждения job может сравнить ограниченный отпечаток `index.html`, число публичных файлов и наличие критических legacy-модулей. SSH у R120 нет.
6. **R121** после подтверждения job может отдельно запустить строго read-only non-root public hash collector по pinned SSH. Он передаёт только SHA-256 допустимых публичных файлов верхнего уровня, без содержимого или персональных данных. Ни один недостоверный R118 не должен достигнуть SSH-этапа.
7. На PR проводятся действующие R120/R121 tests, 14 регрессионных проверок R123 и 14 тестов R124 на целостность workflow, порядок допуска, stale SHA, SKIPPED VPS и запрет записи. Неудачный тест закрывает релиз вместо ложного PASS.

## Ограничения

- Эта работа не создаёт новое доказательство исполнения R118 на Contabo. Оно должно появиться после полного STAGING → R116 → R117 → R118 workflow **на точном коммите**.
- GitHub `workflow_dispatch` R120/R121 по-прежнему не является разрешением на production. Для real read-only job нужен настоящий `workflow_run` R118, успешно выполнивший `live-production-parity`.
- Даже после R121 `PASS` нужна вторая независимая реальная R121-выгрузка для R122.
- Полный независимый бэкап/восстановление реальных Auth, PostgreSQL/Storage, compatibility старых API и решение об изменении домена остаются **NO_GO**.

Изменения затрагивают только шесть workflow (R116–R121) и новые offline-тесты. Никакой записи в `marcosa.club`, SQL, Nginx, DNS и пользовательские данные нет.
