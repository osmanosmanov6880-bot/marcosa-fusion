# MARCOSA R55 — модерация медиа и изоляция Storage: проверяемый PostgreSQL-контракт

**Важно:** это **не** рабочий Supabase Storage и не автоматическая миграция. Здесь реализована отдельная схема метаданных в disposable PostgreSQL 17, которую необходимо пересмотреть перед переносом на реальный проект.

## Что содержится в коде

Таблица `marcosa_private.world_cover_assets` хранит только: UUID мира, реального владельца, внутренний ключ `world-covers/{world_id}/{sha256}.png`, контрольный SHA-256, MIME=`image/png`, размеры, число байтов, факт нормализации и жизненный статус `pending / approved / quarantined / removed`.

Никаких исходных файлов, байтов изображения, персональных EXIF/ICC-метаданных, `public_url`, длинноживущих подписанных ссылок или кредитных данных в манифесте нет.

**Защита:** схема не открыта browser `anon/authenticated`, RLS включён, клиентских SELECT/INSERT/UPDATE/DELETE нет. SQL-триггер `SECURITY INVOKER` проверяет, что реальный `marcosa_worlds.owner_id` совпадает с загрузчиком, а ключ содержит правильный UUID мира и SHA. Перед подтверждением требуется нормализация и независимый модератор (не автор файла); удаление модератора с подтверждёнными материалами запрещено, пока не решён вопрос сохранения аудиторского следа.

## Обязательная логика будущего trusted backend

1. После реального Auth/JWT проверить владельца и квоты, получить файл с жёстким размером и типом.
2. Изолированный worker проверяет байты, декодирует и заново кодирует разрешённый формат, удаляет метаданные, при необходимости сканирует и отправляет на модерацию.
3. Загрузить файл через **Storage API**, в закрытый bucket. Никогда не делать INSERT/DELETE в `storage.objects` SQL: это только метаданные и удаление строки не удаляет объект у провайдера.
4. Сервер пишет `pending` в закрытый манифест и не отдаёт подписанные ссылки гостям до состояния `approved`.
5. Независимый модератор подтверждает контент, сервер проверяет принадлежность World и отдаёт краткоживущую signed URL для законного просмотра. Отзыв/удаление в Storage API должен быть атомарно согласован с манифестом и журналом, иначе возможны сиротские объекты и затраты.
6. Удаление World/аккаунта требует дополнительной задачи очистки **реальных файлов** из Storage и проверки полноты удаления. SQL FK-каскад чистит только манифест, не S3 bytes.

## Реальная проверка

`tests/postgres/70_rls_private_media_manifest.sql` в GitHub Actions проверяет три реальные SQL-идентичности как роли, запрет доступа `anon/authenticated`, правильную привязку к владельцу, запрет публикации без отдельной модерации, отсутствие обхода лимита пикселей и удаление метаданных вслед за World. Испытание изолировано на `postgres:17-alpine`, а не на чужом сервере или реальном Supabase.

**Не завершено:** реальный project URL/Storage credentials, закрытый bucket, правила Storage, worker для медиа, процессы юридической/модерационной проверки и безопасная зачистка S3. Всё это остаётся внешним Gate в [Issue #55](https://github.com/osmanosmanov6880-bot/marcosa-fusion/issues/55).
