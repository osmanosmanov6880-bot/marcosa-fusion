# MARCOSA R72 — независимые жалобы и отзыв опубликованного медиа в PostgreSQL 17

**Сфера:** независимая исполняемая SQL-проверка в disposable PostgreSQL 17. Это не миграция, не действующий Supabase Storage и не разрешённая публичная публикация.

## Что добавлено

- Приватная `marcosa_private.world_cover_reports`, связанная с World, текущими метаданными обложки и идентичностями Auth; ограниченные основания жалобы, описание 12–500 символов и однократное решение.
- Серверная запись `INSERT` допустима лишь для чужой **действительно опубликованной** обложки: UUID мира и владельца, нормализация изображения, SHA-256, действующее независимое одобрение, публичный World и отсутствие взаимной блокировки.
- Решение допускается только от другого независимого модератора: не владелец World, не заявитель и не первоначальный модератор файла. Проверяется **текущее** `auth.users.raw_app_meta_data`, а не редактируемое `raw_user_meta_data`.
- `dismissed` сохраняет опубликованную обложку. `upheld` **в том же SQL UPDATE/transaction** переводит исходное конкретное изображение в `quarantined` и снимает его eligibility в существующем `world_cover_delivery_ready`. Остальные открытые жалобы автоматически становятся `withdrawn`. Реплей решений и изменение обстоятельств жалобы запрещены.
- Существующий механизм независимой апелляции R58 остаётся применим после подтверждённого удаления публичного PNG. Удаление World удаляет связанные обращения и апелляции через FK.
- Ключи Storage остаются в закрытой схеме; клиентским ролям `anon` и `authenticated` не выдаются права на таблицу, API-маршрут создания жалобы или обход модерации.

## Проверенная архитектура безопасности

Официальные основы: [Supabase Row Level Security](https://supabase.com/docs/guides/database/postgres/row-level-security), [Data API access](https://supabase.com/docs/guides/api/securing-your-api) и официальный changelog. Читатель PostgreSQL в приложении должен использовать серверную сессию с ограниченными полномочиями; `service_role` нельзя класть в браузер. Создание и проверка bytes PNG требует отдельного медиапроцессора, работающего с приватным Storage API, а не SQL-модификаций `storage.objects`. Клиентские роль и user_metadata не считаются источником доверия.

## Что проверяет независимый PostgreSQL CI

`tests/postgres/100_private_cover_reports.sql` исполняется после R30–R61 в совершенно новой PostgreSQL 17. Тестирует запрет доступа клиентских ролей, настоящие FK, невозможность жалобы владельца, неправильный SHA-256, взаимную блокировку, запрет предрешённого отчёта, поддельные user_metadata, запрет самопроверки, одобрение/отклонение независимым модератором, автоматический отзыв media eligibility, апелляцию и каскадное удаление. Никакой пользовательский Supabase-проект не изменяется.

## Нерешённые требования

Подключить и проверить существующий **отдельно одобренный** Supabase-проект с живыми Auth/JWT, Data API grants, RLS, приватным бакетом, malware/CSAM policy и легальной процедурой notice-and-takedown. Нужны журналы решений без утечки личных данных, verified proof-of-rights, TTL выдачи подписанных ссылок, отзыв полномочий, legal intake, 24×7 операторы, экспорт/удаление и incident response. Этот reference SQL **не применять к production как готовую миграцию**; только через `supabase migration new`, reviewer/security advisors и тесты двух идентичностей в STAGING после появления доступного проекта.
