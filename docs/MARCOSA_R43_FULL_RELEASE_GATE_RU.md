# MARCOSA R43 — фактическая карта до закрытой беты и мирового коммерческого релиза
Дата аудита: 25 октября 2026.

## 1. Что реально существует

MARCOSA имеет две разные поставки. Первая — публичный статический Network OS Preview на GitHub Pages. Вторая — **реальный исполняемый, но изолированный loopback-сервер Node 22 + SQLite** в `server-lab/`. Это **не один и тот же production-сервис**: публичная страница не получила автоматически настоящие сессии, пользователей и транзакционную PostgreSQL-базу.

Фактически сохранены в `main` и пройдены реальные автоматические тесты: R31 (Following/inbox), R32 (апелляции), R33 (Postgres RLS contract), R34 (локальный SQLite backup/restore), R35 (owner insights без выдуманного дохода), R36 (loopback Host/Origin), R37 (доступ к уведомлениям и апелляциям), R38 (World Builder), R39 (смена пароля + отзыв сессий), R40 (блокировки + отзыв взаимного рекламного согласия), R41 (Postgres RLS для приватного списка блокировок). R42–R43 уже объединены и протестированы; последующие R45–R52 добавили реальные одноразовые приглашения и onboarding, SQL-приватность приглашений, фактическую статистику пилотной аудитории, fail-closed проверку релизных доказательств, настоящую локальную HTTP-нагрузку, пользовательское управление уведомлениями, owner-only PostgreSQL reference-RLS и тематический Discover с безопасной миграцией старых SQLite миров. Это работа локальной лаборатории и disposable CI; не внешняя production-публикация.

**Ни один из этих фактов не доказывает наличие действующих реальных пользователей, проданной рекламы, живой production Auth или мира с миллионами участников.**

## 3. Порядок зависимостей (без сокращений)

**Gate A — доверенный STAGING.** Проверить актуальный SSH host key независимым каналом владельца сервера в панели провайдера, сверить hostname/IP, согласовать причину ротации, затем заменить *только подтверждённый публичный* pinned host key в GitHub environment. `ssh-keyscan` сам по себе не подтверждает идентичность. Скрипты не должны ослаблять StrictHostKeyChecking. Подтвердить изоляцию от текущего production домена.

**Gate B — единая настоящая идентичность.** Подключить существующий Supabase/ PostgreSQL проект через владельца, read-only обследовать Auth/Data API, базовые роли/таблицы и Security Advisor. Не создавать новый проект/двойную базу без согласования стоимости и миграции. Применять сначала миграции к отдельной STAGING/branch среде, проверить rollback и SQL с настоящими JWT. Приватные операции (модерация, блокировка, списание денег) оставить за доверенным сервером.

**Gate C — защищённый вертикальный срез.** Гость читает настоящий опубликованный публичный World; приглашённый автор подтверждает email, создаёт приватный черновик, публикует World, получает ответ и уведомление; блокирует автора, оформляет жалобу и апелляцию; экспортирует/удаляет данные. Все действия проходят на реальном Postgres под RLS. Каждый шаг измерен сквозным браузерным тестом на ПК/телефонах с отдельными пользователями.

**Gate D — законный контент и платежи.** После C — подписанные права на изображения/видео, подтверждение рекламодателей, серверные подписанные счётчики только фактических показов, антифрод, договоры, налоги/НДС по юрисдикции, политика возвратов, подтверждённые вебхуки платежей и только тогда включение коммерческих кампаний.

**Gate E — закрытая бета и решение о масштабировании.** 10 качественных интервью с авторами и 10 с рекламодателями, 10 новых пользователей в usability без подсказок, затем до 100 добровольно приглашённых founders. Считать активацию, повторное возвращение, полезные ответы и реальные письменные рекламные заявки. Не объявлять PMF по лайкам/заполненной карточке. Расширение географии только после доказанной надёжности и спроса.

## 4. Перед public release — явные стоп-условия

Production запрещён при любом из условий:
- нет подтверждённой идентичности STAGING / существует mismatch pinned SSH host key;
- нет доступного проверенного Postgres/Auth проекта и результатов RLS тестирования настоящими JWT;
- отсутствует безопасная работа с изображениями, CSAM/abuse escalation и модерацией;
- нет независимого backup/restore trial и подписанного плана инцидентов;
- отсутствуют юридически корректные согласия, privacy/terms и маршрут удаления данных;
- объявления о оплаченной рекламе без реальных контрактов, подтверждённых оплат и измеренного delivery;
- провал E2E/Chromium/мобильных тестов на актуальном SHA;
- отсутствует способ безопасного отката и критерии остановки кампаний.

**Отдельная публикация статического GitHub Pages не снимает ни один из этих запретов для социальной сети.**

## 5. Минимальный пакет подтверждения каждого релиза

- SHA, PR, зелёный CI именно этого SHA, список функций и миграций;
- результат RLS с двумя-тремя настоящими JWT клиентами и анонимным пользователем;
- staging URL, реальный TLS сертификат, signed host key и журнал smoke-тестов;
- исходники и собранные артефакты + воспроизводимость;
- доступность, UX на телефонах, WCAG, нагрузка, ошибки, реальный откат;
- юридические и операторские ограничения, сведения о реальном платеже/без оплаты;
- реальные показатели использования, без синтетических «подписчиков»/«выручки».

## 6. Что требуется от владельца инфраструктуры

В настоящий момент подключённый Supabase показывает **0 доступных проектов**. Секреты для чужого проекта нельзя угадывать; нужен законный доступ к своему существующему проекту или осознанное создание нового после проверки стоимости. В STAGING GitHub Actions зафиксировал **Pinned host key mismatch**, включая повторный запуск #40118928351. Значит, требуется независимое подтверждение актуального публичного host key владельцем сервера. Не присылать приватные ключи, пароли, service_role или содержимое GitHub Secrets в чат.

Внешний провайдер платежей, домен, юридическое лицо и пользователи должны быть реально подключены и проверены отдельно. До этого код лаборатории можно тестировать, но нельзя объявлять мировую коммерческую платформу готовой.

## 7. Принцип приёмки

Номер R и наличие PR — не критерий Done. **Done** означает: функция работает у независимых пользователей на согласованной среде, прошла CI + ручную приёмку, безопасно сохраняет данные, имеет мониторинг, резервную копию и откат. Если внешний этап заблокирован — статус **BLOCKED**, а не SUCCESS.
