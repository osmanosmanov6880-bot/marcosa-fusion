# MARCOSA R33 — проверяемая статистика персональных миров

## Результат
В R31 в main уже были настоящая приватная лента активности и публикации от Worlds, на которые подписан пользователь. R33 развивает это **без дублирования хранилищ уведомлений**.

- GET /api/me/insights: authenticated, owner-only API, все числа вычислены из SQLite внутри текущего персонального World. 
- На каждую страницу World: опубликованные посты, приватные черновики, число подписчиков, видимые ответы и число **уникальных** пользователей, ответивших на опубликованные истории.
- Вся сводка считает реальные объекты, а не сессии, страницу, показы, цену рекламы или маркетинговые оценки; поэтому paidViews и advertisingRevenue = null.
- Интерактивная кнопка «Обновить статистику» в личном кабинете. Содержимое только через textContent.
- SQL-фильтры защищают приватность: комментарии к черновикам и скрытые модерацией ответы НЕ входят в публичные показатели.
- E2E на HTTP+SQLite и Chromium desktop/390/360, контрольная проверка изменения цифр после действия другого реального пользователя.

## Приёмочные условия
1. Гость получает HTTP 401. Другой пользователь не видит мои черновики, Worlds или внутренние счётчики.
2. Из БД A: 1 опубликовано, 1 черновик, 1 подписчик, 3 ответа от двух уникальных людей. API показывает exactly 1/1/1/3 и uniqueResponders=2.
3. При переводе опубликованного поста в черновик ответы больше не считаются — метрика обновляется из первоисточника.
4. Не выдавать estimate рекламы или доходов: рекламная модель R30 — неоплаченный локальный пилот.
5. Существующий PR R31 Following feed и private activity не переписан. R33 не создаёт второе уведомительное хранилище и не пытается скрыть merge conflict конкурирующих веток.
6. Node + настоящий Chromium (ПК и два телефона), скриншоты, CI зелёные до слияния.

## Нельзя говорить, что это production
GitHub Pages не содержит подключенного multi-user сервера. В Supabase-коннекторе по-прежнему нет доступных проектов для проверки и включения Auth/RLS; внешний STAGING заблокирован несоответствием SSH-ключа. Revenue dashboard, настоящие платные рекламные контракты и миллионы пользователей не запускались.

## Дальнейшие шаги
1. Подключить и проаудировать существующую production-базу без дублирования пользовательских данных.
2. Реализовать в Postgres/RLS защищённый read-model для creator insights; не открывать таблицы шире нужного.
3. Добавить retention-когорты и meaningful replies с зафиксированной методикой, только после реального трафика и согласий пользователей.
4. Продолжить P0 R29: безопасный STAGING, verified identity, медиа, moderations, backup/restore. Коммерческий Ads Manager — после реальных рекламодателей, billing и fraud-review.
