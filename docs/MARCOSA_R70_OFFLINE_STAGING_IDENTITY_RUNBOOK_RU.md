# MARCOSA R70 — независимая проверка SSH host key перед STAGING

**Назначение:** помочь владельцу безопасно устранить ранее обнаруженное несовпадение SSH host key **без отключения StrictHostKeyChecking**. Утилита не подключается к серверу, ничего не развёртывает и не раскрывает личные ключи.

## Что обязан сделать владелец

1. Войти в доверенную панель хостинг-провайдера **самостоятельно** и получить подлинный ED25519 SHA-256 fingerprint именно используемого STAGING-сервера. Не доверять скриншоту из переписки, неизвестной команде `ssh-keyscan` или ключу, взятому с потенциально подменённого канала.
2. Получить публичную запись `known_hosts` для точного `hostname` и SSH-порта. Отдельно проверить её fingerprint с тем, что показан в панели провайдера. Публичные ключи сервера (не приватные ключи клиента) допустимы для этой проверки.
3. Выполнить **локально**:

```bash
node ops/verify-staging-host-key.mjs \
  --hostname staging.example.org \
  --port 22 \
  --known-hosts ./known_hosts \
  --expected SHA256:ИМЕННО_ПОДТВЕРЖДЕННЫЙ_ПРОВАЙДЕРОМ_FINGERPRINT
```

Последняя строка — **место для настоящего fingerprint**, не готовое значение. Утилита возвращает `ok:true` и `localMatch:true` только при точном совпадении. Значение `providerProvenanceVerifiedByTool:false` напоминает, что источник отпечатка подтверждает человек, а не скрипт. `networkContacted:false`: обращений к VPS нет.

4. Только после проверки через независимый канал исправить закреплённую запись публичного host key в секретах GitHub, не отключая `StrictHostKeyChecking=yes`. **Никогда не присылать в чат или issue клиентские SSH private keys, пароли, токены доступа или содержимое `MARCOSA_SSH_KEY`.**

## Что проверяет код

- Только точная hostname/port пара; для не-22 порта требуется формат `[host]:port`.
- Только неповреждённый двоичный ED25519 public host key, корректный SSH-wire формат и точное вычисление OpenSSH SHA256 fingerprint.
- Любое отличие fingerprint, неправильный алгоритм, другой hostname, порт, неоднозначные записи, symlink файл или невалидный base64 приводят к отказу.
- CLI читает только локальный файл; не вызывает `ssh-keyscan`, не создаёт и не заменяет `known_hosts`, не устанавливает соединение и не меняет секреты.
- GitHub Actions проверяет это на **синтетических публичных** ED25519 записях. Никаких реальных ключей доступа в тестах нет.

## Незакрытые внешние условия

Даже успех этой утилиты **не доказывает**, что пользователь сверил expected fingerprint с настоящим владельцем VPS, что STAGING готов, а GitHub runner имеет подходящий ключ клиента. Действующий `scripts/diagnose-staging-ssh.sh` всё равно обязан пройти реальное read-only подключение через `StrictHostKeyChecking=yes`. Закрытая бета и международный выпуск остаются под управлением Issue #55; Supabase Auth/Storage, юридическая приёмка и производство ещё не готовы.
