# MARCOSA R104 — проверка возможности безопасного canary на основном домене

## Доказательства, на которых основан план

- Основная платформа `https://marcosa.club/` обслуживается через `/opt/marcosa/current` и содержит модули, отсутствующие в отдельном GitHub Pages preview.
- Подтверждённый R101 аудит: 34 старых публичных файла верхнего уровня; в новом статическом предпросмотре 62; общий путь верхнего уровня только `index.html`, причём его SHA-256 отличается.
- Новый релиз `c01a153...` был загружен автоматически на Contabo и успешно прочитан по HTTP на `127.0.0.1`: `VPS_HTTP_FILES_VERIFIED=62`. Никакой отдельный публичный HTTPS на VPS пока не заявлен.
- Пользователь `marcosa-deploy` не имеет разрешения перезаписывать `/opt/marcosa/current`. Это **полезная защита**, а не неисправность SSH.

## Рекомендуемая архитектура, не затрагивающая пользователей

**Никакой подмены корня сайта или конфигурации Supabase.** Предлагаемый новый раздел `https://marcosa.club/network-os/` должен открывать отдельный статический, изолированный предпросмотр. Существующие маршруты `/`, `/api`, `/worlds`, `/messages`, логин и БД остаются в старом приложении.

### Подготовительный шаг — только чтение

GitHub Action `.github/workflows/marcosa-r104-canary-readiness.yml` запускает `ops/production_canary_readiness.py` на проверенном VPS под `marcosa-deploy`:
- фиксирует SHA-256 публичных индексов, удостоверяется в одобренном STAGING и проверяет, изменился ли живой `index.html` относительно R101;
- анализирует только известные *структурные признаки* конфигурации Nginx (HTTPS, домен, root, количество location и include, конфликт `/network-os/`);
- **не скачивает конфигурацию Nginx, исходный JS с настройками, токены, БД или личные данные**;
- не выполняет `sudo`, `nginx -s reload`, удаление файлов, смену прав или публикацию в интернет;
- всегда возвращает `productionCutoverAuthorized:false`.

### Следующий шаг — только после надёжной root-controlled процедуры

Для включения отдельного маршрута требуется сделать резервную копию действующего Nginx site-файла, настроить отдельный сервис или read-only webroot для статических артефактов, запустить `nginx -t`, проверить новый URL по HTTPS и предусмотреть мгновенный откат только новой location. Это отдельный **административный** доступ, не тот ключ, которым GitHub публикует в частную STAGING-папку.

Перед реальной активацией:
1. Доказать, что маршрут `/network-os/` не занят.
2. Сохранить существующий `marcosa.club` полностью без удаления кода/модулей.
3. Подтвердить, что новый предпросмотр не использует production cookies/Auth/Supabase/платежи.
4. Проверить обратный путь: отключение нового маршрута не меняет старые страницы.
5. Настроить отдельное публичное HTTPS-readback после canary, а не считать локальный HTTP доказательством публичности.

**Результат R104 — отчёт, а не переключение:** отсутствие sudo/root у deploy-ключа не надо обходить и не следует выдавать за ошибку. Не выдавать опубликованную статическую демоверсию за полноценную многопользовательскую платформу.
