# MARCOSA R127 — независимое повторное подтверждение двух R118 VPS-аудитов

**Релизный статус:** только read-only preflight; `productionDecision=NO_GO`. Изменений `marcosa.club`, DNS/Nginx, Auth, PostgreSQL/Storage, учётных записей или production-файлов нет.

## Какой пробел закрывается

R126 научил R121 прикреплять проверенный R123 upstream receipt с `verifiedR118UpstreamRunId`. R122 проверяет два разных R121-запуска, настоящие jobs и артефакты и отвергает один и тот же исходный R118 ID дважды. Но сам R122 до R127 **не вызывал API GitHub для проверки исходных R118**, полагаясь на защиту R121.

R127 создаёт второе, независимое подтверждение из GitHub API: получает **каждый конкретный R118 run ID**, его jobs, артефакты и публичный ограниченный NO_GO-отчёт по номеру, переданному проверенным R121. Никаких поисков «последнего зелёного» или доверия только общему `success`.

## Реализованная проверка

1. R122 вручную запускается с двумя различными R121 run ID на **точном текущем main SHA** и загружает обе ограниченные R121-инвентаризации.
2. R127 в режиме `--parent-ids` извлекает из этих двух отчётов ровно два положительных и отличающихся `verifiedR118UpstreamRunId` и тот же SHA. Эти ID используются исключительно для read-only запросов.
3. Для **каждого** R118 запрашиваются метаданные `actions/runs/{id}`, полный список jobs, артефакты и ограниченный `marcosa-r118-production-boundary-no-go`. Не используется SSH, личная БД или доступ к production-файлам.
4. Повторно вызывается действующий `verifyR118LiveEvidence` (R123). Дополнительно R127 требует `workflow_dispatch` на `main`, точный SHA, полный список jobs, ровно один настоящий `live-production-parity=success`, отдельный успешный offline job и **свой** ещё действующий R118 NO_GO-артефакт с конкретным run ID.
5. Сверяются публичный индекс и количество файлов из R118 с данными соответствующего R121, отсутствие DRIFT, совпадение порядка пар R118 IDs с R122 и различие ID настоящих VPS jobs и артефактов у двух исходных R118.
6. Только после собственного R122 `PASS` R127 записывает отдельный **ограниченный** `marcosa-r127-independent-r118-parent-proof.json`; тот же run выгружает R122 и R127 отчёты как артефакты. Каждый отказ даёт ненулевой код, без фиктивного PASS.

## Ограничения

- Это подтверждение **метаданных и ограниченных NO_GO-отчётов из GitHub**, а не криптографическая аппаратная подпись сервера.
- Разные R118 и R121 подтверждают независимые завершённые проверки **публичных хешей в момент двух снимков**, но не доказывают неизменность всех данных во все прошлые моменты.
- Никаких проверок реального входа, сессий, RLS, MFA, пользовательского Storage, восстановления PostgreSQL и удаления аккаунтов этот блок не выполняет.
- Без доступа к правильному исходному проекту Auth/Postgres/Storage невозможно утверждать, что реальная миграция безопасна.

## Строгий порядок реальной проверки

На одном **неизменившемся** SHA: Pages HTTPS + STAGING → действительный R116 настоящий SSH proof → ручной R117 → два отдельных вручную запущенных R118 с действительными артефактами → две связанные R121 real-VPS инвентаризации → ручной R122 (внутри него R127 проверяется автоматически). Каждый следующий merge меняет SHA и обнуляет пригодность старых доказательств для нового HEAD.

После этого отдельно требуются юридический/security approval, Auth/RLS совместимость, PostgreSQL+Storage backup/restore с проверенной изоляцией пользователей и подтверждение владельца. До них **PRODUCTION NO-GO**.
