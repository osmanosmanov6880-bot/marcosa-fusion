# MARCOSA R89 — честная эксплуатационная готовность SQLite и аварийные режимы

**Что реализовано:** реальная локальная диагностика доступности/целостности
Node.js 22 + SQLite. Это **не** производственный SLO, PostgreSQL PITR,
cloud health / DR, проверенный RTO или мониторинг 24/7.

## Что исправлено

Ранее `GET /api/health` возвращал `ok:true`, когда HTTP-процесс
отвечал — независимо от сохранности внешних ключей в базе.
Это корректная **liveness**-проверка, но её нельзя считать
доказательством готовности данных.

R89 добавляет специальный операторский
`GET /api/mod/readiness`:

1. Отказ анонимному запросу HTTP 401, обычному участнику 403,
   доступ только авторизованному текущему модератору. Проверка
   роли выполняется при каждом запросе, чтобы разжалованный
   модератор сразу терял доступ.
2. На каждом **явном запросе** запускаются
   `PRAGMA quick_check(1)`, `PRAGMA foreign_key_check` и
   проверка существования обязательных таблиц в `sqlite_master`.
   Это отдельная тяжёлая диагностика по запросу, её не стоит
   подключать к частому внешнему heartbeat или интернет-мониторингу.
3. При обнаружении нарушения ответ HTTP **503**, с
   `Cache-Control: no-store`, `Retry-After: 60`.
   Ни SQL, ни путь SQLite, ни имена, ни тексты пользователей,
   ни ключи доступа не возвращаются. Обычный `/api/health`
   при этом по-прежнему сообщает о жизнеспособности процесса,
   а не «полной готовности».
4. Различает `readReady`, `writeReady` и
   `publicMediaReady`. Если R79 или R81 включили
   аварийное ограничение, корректная БД остаётся **читаемой**,
   но публикация/выдача изображений помечается отдельно
   как выключенная.
5. Применённая дизайн-система MARCOSA: вкладка модератора
   «Целостность локальной базы», видимая кнопка проверки,
   aria-live статус и RU/EN локализация без передачи
   пользовательских сведений сторонним сервисам.

## Независимая приёмка и доказательства

```bash
node --test server-lab/test/r89.sqlite_readiness.test.mjs
node server-lab/test/r89.readiness_browser_cdp.mjs
```

Первый тест поднимает настоящий HTTP и постоянную SQLite на диске:
проверяет guest/member/moderator, здоровый статус, создаёт
одну несуществующую FK-ссылку при отключённом enforcement
**только в disposable fixture**, получает от readiness HTTP 503,
убеждается в отсутствии персональных данных, удаляет повреждённую
ссылку и получает HTTP 200 без потери настоящих данных.
Затем закрывает и снова открывает SQLite с R79+R81,
проверяет чтение при запрещённой записи/публичных PNG и
немедленную потерю доступа после понижения роли модератора.

Второй запускает Chromium 1440/390/360,
проверяет реальную кнопку модератора, aria-live, точную
RU/EN статусную строку, отсутствие горизонтального переполнения,
посторонних HTTP запросов, JS exceptions; сохраняет шесть
скриншотов для независимого ревью.

**Границы:** `quick_check(1)` не равен полному
`PRAGMA integrity_check` или независимому восстановлению
резервной копии; этот операторский показатель сам по себе
не может подтвердить производственный SLA/SLO, RPO/RTO,
устойчивость нескольких серверов, PostgreSQL/PITR,
Supabase Storage, CDN, аварийную эвакуацию ключей
или безопасность политики прав. Критерии R89 глобальной
эксплуатации остаются открыты до измеренных drill,
пентеста и проверки внешнего STAGING/production.
