# MARCOSA R51 — приватные настройки уведомлений в PostgreSQL

Крупный блок продолжает реальную функцию R50, но проверяет **будущий многопользовательский контракт** отдельно от Node/SQLite. Применение к действующему Supabase НЕ выполнялось.

## Реализованная SQL-модель

- `public.marcosa_notification_preferences`: пользователь из `auth.users`, три отдельные булевы категории: `follows_enabled`, `comments_enabled`, `sponsorships_enabled`; по умолчанию `true`, без хранения секретов или личных предпочтений других людей в открытом доступе.
- `PRIMARY KEY(user_id)` и `ON DELETE CASCADE`: ровно одна строка на владельца, приватные настройки удаляются при удалении аккаунта.
- `ENABLE ROW LEVEL SECURITY`, отзыв всех разрешений `anon`/`authenticated` и разрешение `SELECT` только с `user_id = (select auth.uid())`.
- Клиентским ролям не предоставлены `INSERT`, `UPDATE`, `DELETE`. Реальные изменения и серверное соблюдение выбора при записи нового activity event потребуют доверенный backend с верифицированной личностью, ограничением частоты и журналом согласия.

## Проверки в GitHub Actions

В disposable PostgreSQL 17 создаются три независимые личности D/E/F; проверяются значения по умолчанию, персональная строка пользователя, запрет чтения чужих данных, запрет изменений через browser JWT, обработка серверного обновления без затрагивания другого аккаунта, удаление аккаунта и FK-каскад.

Запуск встроен в `.github/workflows/marcosa-postgres-rls-reference.yml` после R30/R37/R41/R43/R46. Реальные учетные данные или production базы не используются.

**Ограничение:** R51 — SQL-контракт, не полная миграция в Supabase и не service-role endpoint. Для публичного релиза остаются реальная Auth/email verification, HTTPS, JWT/RLS в доступном проекте, защищенный STAGING, реальная аудитория и согласованное хранение данных.
