# MARCOSA R43 — проверка приватных сохранений в PostgreSQL

Этот этап расширяет проверяемую модель PostgreSQL после R30/R37/R41, чтобы в будущей многопользовательской базе личная коллекция сохранений была привязана к конкретному владельцу.

## Реально подготовлено

- `public.marcosa_saved_posts`: пользователь, исходная запись, время сохранения, уникальная пара user/post.
- Включён Row Level Security, браузерный `authenticated` может выбирать только строки, у которых `user_id=(select auth.uid())`.
- Анонимная роль не получает `SELECT`. Клиентские `INSERT/UPDATE/DELETE` запрещены, чтобы их нельзя было выполнять в обход backend-проверки статуса публикации и взаимных блокировок.
- Исходные записи остаются у автора; удаление записи или аккаунта каскадно очищает сохранения. Ни просмотры, ни рекламные показы из этих данных не выводятся.
- CI с настоящим PostgreSQL 17 и симулированными Alice/Bob/Carol проверяет выборку собственных ссылок, запрет чужого чтения/подделки/удаления, уникальность и FK-каскад.

## Что это **не** завершает

- Это reference SQL, а не применённая миграция в существующий Supabase (доступного проекта в подключении пока нет).
- SELECT содержит только owner-bound metadata; полный текст и поля оригинального поста требуют независимого RLS на `marcosa_posts`, проверки статуса публикации и серверной проверки взаимных блокировок. Применение схемы к реальной БД без backend-фильтра запрещено.
- При создании/удалении сохранений настоящий доверенный сервер должен проверять JWT, статус публикации, права модерации, блокировки, лимиты и идентичность; этот интерфейс в PostgreSQL пока не создан.
- Нужны отдельно подтверждённый Supabase Auth, Security Advisor, STAGING, восстановление PostgreSQL, политика хранения и закрытая бета.

**Правило приёмки:** PR не объединять до успешного исполняемого PostgreSQL CI. Не публиковать приватные данные или сервисный ключ.
