# MARCOSA R84 — PostgreSQL: взаимная блокировка и отзыв подписок

**Внесён реальный исполняемый SQL-контракт и отрицательные PG17-тесты.**
Это **не** развернуто в Supabase Auth/Data API; проект Supabase пока
не выбран и не доступен. Фактическое внедрение требует миграции в отдельно
разрешённый STAGING, RLS advisor и тестов настоящих JWT.

## Конкретный риск, который исправлен

Исходная таблица R41 `marcosa_user_blocks` разрешает
аутентифицированному пользователю читать **только свой исходящий**
список блокировок. Обычный RLS предикат поэтому не мог надёжно
проверить **входящую** блокировку: Bob не видел в собственной
RLS-сессии, что Alice уже заблокировала Bob. Переход к
`USING true` или раскрытие чужого списка нарушил бы приватность.

R84 вводит строго ограниченную вспомогательную схему
`marcosa_authz`, которая **не должна быть опубликована в Data API**.
`marcosa_authz.interaction_allowed(actor,target)` выполняется
в контексте доверенного владельца SQL, но возвращает только boolean
после жёсткой проверки `actor = auth.uid()`.
Она не возвращает имена/списки/историю чужих блокировок.
При этом этот один бит может косвенно сообщить, что взаимодействие
недоступно, поэтому персональные списки по-прежнему защищены, а
абсолютная тайна факта блокировки **не обещается**.

Переписаны только две RLS INSERT-политики:

1. Новая подписка: только на публичный чужой World, только от
   `auth.uid()`, при отсутствии блокировки **в любом направлении**.
2. Новый комментарий: только на опубликованный пост в публичном World,
   только от `auth.uid()`, при отсутствии любой взаимной блокировки.

Ни клиенты, ни пользовательские `raw_user_meta_data` не управляют
правами помощника. Прямой `INSERT/UPDATE/DELETE` в список блокировок
для `authenticated` по-прежнему запрещён. Само создание блока
должно оставаться проверенной транзакцией trusted backend.

## Атомарное прекращение отношений

Новый SQL-триггер `marcosa_revoke_follows_on_block` после
доверенного INSERT блока удаляет подписки в **обе стороны**,
в той же PostgreSQL-транзакции. Это работает даже если
отношение уже существовало до изменения политики.
Также выполняется разовая инвентаризация и очистка
legacy-follow отношений, запрещённых уже существовавшими блокировками.

Модель не удаляет старые комментарии и публичные публикации:
это было бы ошибочной безусловной потерей пользовательского контента.
Настройки видимости ленты по блокировкам и безопасные внутренние
уведомления потребуют отдельного backend/API контракта. Это не
«полная реализация» всей модерации R84.

## Независимая проверка

`tests/postgres/120_reciprocal_blocks_actions.sql` исполняется только
в disposable PostgreSQL 17 после всех предыдущих R30–R75 тестов.

Проверяет:
- RLS/USAGE/EXECUTE: anonymous не может вызвать helper,
  browser не может создать/отменить блок либо вызвать trigger;
- три отдельные Auth-идентичности из старых тестов остаются
  изолированными; для новых Alice/Bob-like аккаунтов проверяется
  ситуация **до** блокировки, когда follow/comment разрешены;
- защищённый backend INSERT блока удаляет две подписки атомарно;
- у блокирующего и заблокированного теперь не проходят
  повторные follow и комментарии в чужой World;
- пользователь видит только исходящий список, не чужие записи;
- поддельный `actor` не позволяет узнать чужую блокировку;
- собственный опубликованный пост остаётся комментируемым;
- удаление аккаунта удаляет связанные блокировки через FK.

Проверка работает с PostgreSQL-ролями `anon`/`authenticated`
и симулированным `auth.uid()` из `00_auth_fixture.sql`.
Она **не** заменяет реальную проверку Supabase JWT/MFA/session,
проверку выданных Storage ссылок и независимый pentest.

## Последняя продакшен-граница

Перед STAGING обязательно:
- собрать и проверить версионированную миграцию через
  актуальную Supabase CLI после проверки advisor;
- удостовериться, что `marcosa_authz` не раскрыта в Data API;
- провести аудит всего `SECURITY DEFINER` кода, прав владельца
  и наличия `SET search_path = ''`;
- проверить две действительные JWT с противоположными блокировками
  непосредственно через REST и чувствительные приложения;
- испытать откат и восстановление старых данных, проверив
  необратимое удаление follows с согласованием пользователя;
- получить отдельный review безопасности и legal/privacy.

Без реального Supabase-проекта делать `apply_migration` нельзя.
