# MARCOSA Ω — полная карта доведения к мировому выпуску R82–R90

**Дата состояния:** 25 октября 2026. **Статус:** локальная Node 22/SQLite система с множеством реально проверенных модулей; публичный международный production НЕ подтверждён.

Это **полная последовательность выполнения и критериев сдачи**, а не утверждение о том, что все нижеописанные инфраструктурные работы уже осуществлены. Дорожная карта не зависит от произвольных сроков или числа коммитов. Следующая волна запускается только после доказанной приёмки необходимых предыдущих волн.

## R82 — реальный статус инцидента в интерфейсе

**Реализуется в PR R82.** UI получает серверный `/api/health`, объясняет одновременно остановку публикации/PNG, локализуется RU/EN, остаётся доступным с клавиатуры. Chromium проверяет 4 состояния × 3 экрана и снимки. **Выход:** полный green CI на точном коммите и ревью снимков. R82 не меняет cloud configuration.

## R83 — подтверждённая инфраструктура и формальное разграничение сред

**Зависит от внешних действий владельца:**
1. Явно выбрать **существующий**, юридически и финансово одобренный Supabase-проект или запросить разрешённое создание проекта, отдельно для STAGING/PRODUCTION. Организация без проекта не считается подключённой базой. Зафиксировать бюджет, регион данных, владельца секретов и цепочку эскалации.
2. Из панели хостинга независимо подтвердить ED25519 SSH host key и конкретный host:port. Не отключать `StrictHostKeyChecking=yes`. Существующие R70 и SSH preflight подтверждают только локальную сверку, источник значения проверяет человек.
3. Документировать два изолированных окружения, домены, TLS-сертификаты, cookie/domain policy, секреты и запрет доступа PR-веток к production credentials.
4. Создать два минимально-привилегированных операционных аккаунта, отдельный аварийный доступ и процесс ротации.
5. Выполнить read-only STAGING preflight, затем отдельно подписанный deploy и rollback drill.

**Приёмка:** подписанное разрешение на расходы и проект, реальный HTTPS/SSH журнал без отключений защиты, два независимых наблюдателя, однозначное указание deployed commit, успешный откат и отсутствие публикации клиентских секретов. **Не запускать** deploy из предположений о старых ключах.

## R84 — настоящий Auth/JWT + PostgreSQL RLS

1. Перенести **миграциями**, одобренными security review, состояние Worlds, post/draft, follows, comments, reports, appeals, blocked users, rights/provenance и event log в PostgreSQL с требованиями к хранению/удалению.
2. Для exposed schema использовать реальные RLS `USING` / `WITH CHECK`, проверку `auth.uid()`, `SECURITY INVOKER` views. Приватные таблицы не выдавать `anon`/`authenticated` через Data API. Привилегию модератора брать из защищённого app_metadata и проверять актуальность сессии.
3. Реальный Supabase Auth: подтверждённая почта, восстановление, MFA модераторов, rotation/expiration, блокировка сессий, logout-all, анти-бот и anti-enumeration.
4. Создать в **изолированном STAGING** тестовые аккаунты: guest, автор A, автор B, модератор C, отозванный модератор D. Выполнить поддельные owner_id, JWT user_metadata, role downgrade, отозванную сессию, прямые HTTP Data API запросы.
5. Сверить публичный и приватный экспорт, удаление account+media+search/cache, аудит без утечки личных текстов.

**Приёмка:** 100% отрицательных cross-tenant сценариев отвергнуты, старые записи импортированы с подтверждёнными FK, реальные JWT работают в браузере и в Postgres, отмена роли действует немедленно в чувствительных операциях. SQL из CI **не является доказательством реального RLS**.

## R85 — приватная глобальная медиацепочка

1. Загрузка только в Private Storage через доверенный backend и короткоживущий scoped-token; одинаковый digest и storage key, versioned rights statement.
2. Проверка реальных bytes: MIME/magic/PNG, bounding размеров, декодирование в изолированном воркере, удаление метаданных, антивирус и policy проверки, лимиты CPU/памяти/времени.
3. Отдельные состояния: `uploaded_private -> scanning -> pending_review -> approved -> quarantined/deleted`. **Без прямого `public` bucket.**
4. Независимая модерация, жалоба, отзыв `approved`, повторная проверка SHA после замены, owner appeals, immutable action log с ограниченным сроком.
5. Реальный CDN: signed URL небольшой длительности, ревокация на origin, отказ при удалении/демотировании модератора, запрет публичного кэширования персональных файлов.
6. Испытания: 3 пользователей × неправильный slug, пересечения прав, двойная модерация, 403/404 на приватный оригинал, CSRF, malicious PNG, кэшированная старая URL, смена owner.

**Приёмка:** 0 раскрытий непринятых и удалённых PNG через прямой API, CDN или старые ссылки; проверенный экстренный отказ на всех инстансах; подтверждённая процедура notice-and-takedown и инвентаризация legacy-картинок без прав.

## R86 — законная монетизация и проверенная экономика

1. Отдельно удостоверить **какому бизнесу и владельцу принадлежит Stripe/Merchant**, какие операции и регионы разрешены. Подключённый аккаунт другого бренда не использовать как MARCOSA по умолчанию.
2. Утвердить продукты и договоры: бесплатные аккаунты/Worlds, платные функции только с доказанным спросом, партнёрские размещения с рекламной маркировкой, правила возвратов/налогов и возрастные ограничения.
3. Checkout/payment intent только на backend с подтверждёнными условиями, подписанный **raw-body** webhook official SDK, replay/idempotent fulfillment, ledger, возврат, dispute, event ordering.
4. Экономика: реальные выручка–комиссия–возвраты–VAT–support–storage/CDN–moderation–fraud. Отделить реальные суммы от sandbox; все показатели брать из платёжной системы и сверенного ledger.
5. Два финансовых контрольных лица должны подтвердить тестовый возврат, повторную доставку webhook, двойную оплату, отмену и корректное отражение в приложении.

**Приёмка:** реальные документы и платёжный провайдер, тесты отрицательного webhook, zero double-grant, finance reconciliation, подписанный маркетинговый договор. До этого доход = **не подтверждён**, не «ожидаемая выручка».

## R87 — международное качество продукта

1. Зафиксировать полный inventory системных ошибок, alert, moderation reasons, email, уведомлений, кнопок, правовых текстов; заверить RU и EN носителями и юристами.
2. WCAG 2.2 AA для главных сценариев: клавиатура, focus, screen readers, 200% zoom, reduced motion, формы, простые слова. Проверить iOS/Android/desktop на реальных устройствах, а не лишь эмулятором.
3. Переводить UGC **только с разрешения автора/пользователя**, никогда не менять смысл или право владения исходным текстом.
4. SEO канонизация/hreflang только на production домене с проверенным правом показывать опубликованный World; не индексировать приватные и тестовые среды.
5. Производительность: согласовать SLA/SLO после измерения на целевых устройствах; мобильный UX, доступность upload/media, offline/error/low-bandwidth сценарии.

**Приёмка:** исходники перевода + независимая языковая вычитка, реальные устройства, отчёт accessibility с исправленными blocking issues, нет утечек UGC и ложных публичных счётчиков.

## R88 — настоящая закрытая международная бета

1. Пригласить настоящих согласившихся участников из нескольких целевых сегментов; не подменять их 12 лабораторными профилями. Заполнить метки страны/языка **только при законном обосновании и согласии**.
2. Наблюдать активацию: World создан, описание заполнено, первая публикация, follow, ответ, сохранение. Отдельно учитывать рекламодателей и честные заявки.
3. Opt-in event days с реальным UTC и добровольной возможностью удаления; D7 и D30 фиксируются **только после реальных 7/30 суток** и зрелых когорт.
4. Провести независимые интервью, пользовательские тесты и выявить причины отказа, долю завершивших onboarding, модерационный backlog и трудность приглашения коллег.
5. Сегментировать вывод по ранним участникам и каналам. Результаты показывать с знаменателями/доверительным интервалом там, где уместно, без фиктивного «роста x100».

**Приёмка:** доказанное происхождение живых событий и согласий, честные знаменатели, обработка обратной связи, сохранение/удаление данных по запросу, документированный вердикт CONTINUE / PIVOT / STOP.

## R89 — операции, безопасность и отказоустойчивость

1. Мониторинг реального backend: метрики ошибок/latency/storage/scan failures, алерты, on-call, безопасные логи без токенов и чужих текстов.
2. Нагрузочные профили для гипотезы целевой аудитории с доказуемой p95/p99, очереди image processing, отказ одного узла и падение Postgres.
3. Отдельное восстановление PostgreSQL PITR и Private Storage в clean-room, сравнение реально восстановленных bytes/FK, реальный RTO/RPO (не брать из документа без измерения), offsite и ключи KMS.
4. Независимая security проверка: OWASP ASVS/API, CORS/CSRF, SSRF, rate limits, object-level authorization, upload decoding, BOLA/IDOR, secrets scans, SQL/MCP permissions.
5. Аварийная тренировка: остановка выдачи PNG на всем CDN, заморозка публикаций, инцидентный audit, восстановление из проверки, rollback по точному SHA.

**Приёмка:** подписанные акты pentest и restore, границы SLO подтверждены нагрузкой и журналами, секреты не в репозитории, команда отрабатывает инцидент без автора кода.

## R90 — независимый публичный go/no-go

Разрешён только при одновременно выполненных R83–R89:

- Все обязательные exact-head GitHub CI успешны и review approved без старых branch SHA
- Реальные HTTPS/STAGING/SSH/Supabase/JWT/Storage и owner isolation проверены
- Legal/privacy/контентные права и региональные ограничения одобрены
- Медиа не утекали, CDN emergency fail-closed отработан, moderation/appeals доступны
- Реальная бета, D7/D30 с истинной датой и экономическое обоснование, без вымышленных покупок
- Провайдер платежей и договоры подтверждены, finance ledger/replay/refunds протестированы
- DR, backup recovery, rollback, monitoring/on-call и независимый аудит завершены
- Уполномоченный владелец выпуска **отдельно разрешил** production на конкретном commit

Существующие `ops/check-release-gate.mjs` и `ops/release-evidence-gate.mjs`
проверяют доказательства на **конкретном SHA**, но выдача
`READY_FOR_INDEPENDENT_REVIEW` не разрешает deploy.
`productionAuthorized=false` остаётся строгим программным принципом:
последнее право принимается в независимом организационном процессе.

## Минимальный пакет доказательств для каждой волны

`owner / scope / exact commit / code review / SHA+CI links / real HTTP+UI+DB logs / negative security tests / measured user impact / rollback proof / independent reviewer / conclusion / budget and legal signoff`.

**При отсутствии любого критического элемента этап не закрывается**. В задачах CI нельзя помещать API secrets, SSH keys, PII или пользовательские книги/файлы.

## Экономический принцип

Ни одна «мировая» функция не имеет приоритета над действующим user demand и приватностью. Решения о больших платных мощностях принимает финансовый владелец на основе реальной удерживаемости, платёжеспособного спроса и проверенной unit economics, а не из количества планов/коммитов.

**Самый короткий путь к настоящему выпуску теперь начинается не с новой абстрактной функции, а с реального согласованного проекта Supabase, проверенного SSH/STAGING, тестов реальных JWT и Private Storage.** Без этих внешних ресурсов можно завершать и объединять локальные функции, но нельзя достоверно объявлять международный production созданным.
