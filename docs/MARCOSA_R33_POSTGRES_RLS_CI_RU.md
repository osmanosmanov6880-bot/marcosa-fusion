# MARCOSA R33 — проверяемый PostgreSQL RLS контракт

**Это реальная автоматическая проверка SQL на одноразовом PostgreSQL 17, НЕ миграция в production Supabase.**

## Зачем

R30 содержит проект схемы и RLS. До R33 её пригодность для выполнения PostgreSQL не была доказана. Новый GitHub Actions job создаёт чистую PostgreSQL 17 базу прямо на временном GitHub runner, имитирует роли Supabase `anon/authenticated` и функцию `auth.uid()`, запускает **оригинальный** `docs/MARCOSA_R30_POSTGRES_RLS_REFERENCE.sql` без правок и проверяет результат различными идентичностями.

## Что проверяем

1. Anonymous: видит только публичные Worlds/посты/комментарии; не видит черновики, приватные или скрытые записи.
2. Bob: не видит закрытый World Alice или её черновик и не получает имена остальных подписчиков из таблицы подписок.
3. Bob: не может вставить или переподчинить пост в чужой World, изменить чужую публикацию или «захватить» владельца мира.
4. Bob: может создать публикацию в собственном World.
5. Alice: может читать свои черновики и приватные записи; скрытая модерацией запись не становится публичной.
6. Carol: видит только собственные записи подписок, не списки Bob и Alice.
7. Частная таблица рекламных заявок не выдаёт прямых SELECT-прав браузерным ролям.
8. На базовых шести таблицах включён RLS.

**Запуск в CI:** `.github/workflows/marcosa-postgres-rls-reference.yml`. Две SQL проверки `tests/postgres/00_auth_fixture.sql` и `tests/postgres/10_rls_isolation.sql`.

## Чего тест НЕ доказывает

- Не является проверкой реального Supabase JWT, Auth/email verification, project Data API settings, extensions, Storage и нового приложения.
- R30 reference пока **не включает** новые таблицы R31 уведомлений и R32 апелляций; их production RLS и server-only invariants требуют отдельной проектной модели.
- Тестовая функция `auth.uid()` создана исключительно в disposable CI и не заменяет Auth настоящего проекта.
- Не может подтвердить наличие актуального backup/restore, защищённого STAGING, доступность домена, SMTP, платежи или реальную работу с людьми.
- Подключённый Supabase список проектов на момент разработки возвращал 0. Никаких пользователей или SQL в боевую БД не отправляли.

## Критерий будущего продакшена

Сначала определить владельца и существующий проект Supabase; выполнить read-only inventory конфигурации Auth/Data API, безопасный staging/backups. Затем применить проверенные миграции в отдельный тестовый проект, проверить настоящие JWT двух пользователей и актуальный Security Advisor, а уже после переходить к закрытой бете. Никаких client-side секретных ключей и automatic public deploy из этой лаборатории.
