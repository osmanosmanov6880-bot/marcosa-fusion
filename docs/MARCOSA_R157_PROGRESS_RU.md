# MARCOSA R157 — доверенная авторизация, HTTP-команды и контроль очереди

**Разработка:** [PR #168](https://github.com/osmanosmanov6880-bot/marcosa-fusion/pull/168), ветка `feature/marcosa-r150-growth-economics`.

**Область действия:** изолированный Node.js API и отдельный PostgreSQL 17 в CI. На текущем цикле не настроены действующий Supabase Auth, реальные сессии, PostgreSQL-пул для production, отправка уведомлений, пользовательская миграция, платежи или выплаты. Никакого автоматического запуска сервера на публичном адресе нет. Это приложение **не готово к production**.

## Пять крупных реализованных блоков

### R157-1 — проверка JWT и реальной сессии как обязательный контракт

Файл: `ops/r157/identity.mjs`.

- Публичные ключи строго из переданного доверенным оператором JWKS. Не выполняются запросы по `jku`, `x5u`, `jwk` из заголовка JWT.
- Только `RS256` и `ES256`; `HS256`, `none`, подмена `kid`, смешение алгоритмов, приватные ключи в конфигурации и дубли key ID отвергаются.
- Проверяются `typ=JWT`, подпись, issuer, audience, роль `authenticated`, UUID пользователя и `session_id`, `iat/nbf/exp`, максимальный срок токена, признак анонимного аккаунта.
- Для **каждого** запроса на изменение вызывается обязательный доверенный `isSessionActive({sub,sessionId,expiresAt})`. Ошибка/недоступность этой проверки отвергает доступ. В CI ключ и токены генерируются локально.
- **Важно:** production-код реальной интеграции с таблицами сессий и доверенной инфраструктурой Auth ещё не подключён. Нельзя использовать простую подстановку `isSessionActive=()=>true` для реальных пользователей.

### R157-2 — параметризованный PostgreSQL-адаптер и временная роль

Файл: `ops/r157/pg-command-store.mjs`.

- `createCommandStore({pool})` принимает только доверенный серверный пул PostgreSQL-совместимого интерфейса.
- Каждая операция выполняется с `BEGIN`, `SET LOCAL ROLE marcosa_r156_writer`, `set_config('request.jwt.claim.sub',$1,true)`, параметризованным `SELECT marcosa_private.r156_*(...)`, `COMMIT`.
- При ошибке выполняется `ROLLBACK`, соединение возвращается в пул. SQLSTATE переводится в безопасный HTTP-статус без выдачи внутренних ошибок и SQL.
- Без строковой интерполяции пользовательских UUID, заголовков, текста или ревизий. Список допустимых операций жёстко фиксирован.
- `tests/postgres/161_r157_transaction_guc.sql` проверяет на реальной PG17, что роль и идентификатор пользователя очищаются после `COMMIT` и `ROLLBACK`, а неудачная операция не оставляет журнал и ревизию.

### R157-3 — строгие HTTP-команды

Файл: `ops/r157/http-gateway.mjs`.

- Создаётся HTTP-сервер (не запускается автоматически) с семью операциями: `edit`, `reorder`, `publish`, `publication`, `subscription`, `bookmark`, `attendance`.
- На изменение требуются `Authorization: Bearer ...`, разрешённый `Origin`, UUID `X-Idempotency-Key`, `application/json`.
- Точная проверка URL, ограничение количества полей, размера тела до 12 КиБ по умолчанию, длины строк, списка эпизодов, ревизий и допустимых значений. Дополнительные поля, переданный клиентом `actorId`, неверные ключи, дубли эпизодов и чужие Origin отвергаются.
- Ограничитель нагрузки с конечным числом записей и отказом при переполнении; ответы `Cache-Control: no-store` и `nosniff`. Не используется Cookie-авторизация и не раскрываются данные об ошибках PostgreSQL.
- Реальный PostgreSQL backend остаётся подключаемым через проверенный серверный пул; CI использует инъекцию тестового пула, а SQL-функции проверяет отдельно на PostgreSQL.

### R157-4 — окончательная проверка очереди и отмена отозванных задач

Файлы: `docs/MARCOSA_R157_OUTBOX_LIFECYCLE_REFERENCE.sql`, `ops/r157/outbox-simulator.mjs`.

- `r157_delivery_fence`: непосредственно перед обработкой проверяются действующая аренда, её токен, срок и согласие пользователя.
- `r157_cancel`: отмена арендованного задания только по действующему токену; чужой/старый токен не подходит.
- `r157_sweep`: ограниченный `SKIP LOCKED`-проход удаляет из текущей очереди отозванные задания и исправляет зависание попытки №6 в состоянии `leased`. Конечное состояние — `dead`.
- `r157_queue_health`: безопасная сводка количеств `pending/leased/acked/dead/expired/exhausted` без разглашения адресатов.
- Закрытые функции доступны только роли `marcosa_r156_dispatcher`, а не `anon/authenticated`.
- Симулятор строго требует одноразовый GitHub Actions PG17 на loopback и никогда не отправляет настоящих сообщений. Никаких обещаний *exactly once* для будущего внешнего транспорта.

### R157-5 — приёмка API, SQL и восстановления

Файлы: `ops/test/r157.auth-gateway.test.mjs`, `tests/postgres/160_r157_outbox_lifecycle.sql`, `161_r157_transaction_guc.sql`, `162_r157_restored.sql`, `.github/workflows/marcosa-r157-gateway.yml`.

- Подписанные ES256-токены: действительный вход, неверные issuer/aud/role, просроченные и будущие токены, session revocation, подмена подписи, опасные алгоритмы и внешние адреса JWKS.
- Настоящий локальный HTTP: запрещённые Origin, пустая авторизация, подмена автора, ошибочный Idempotency-Key, лишние поля, вредоносный/повреждённый JSON, слишком большой запрос и дубли в порядке выпусков.
- Инъекция PostgreSQL-пула: проверка последовательности `BEGIN → SET LOCAL ROLE → set_config → SQL → COMMIT`, параметров, отката и возврата соединения при ошибке.
- Реальные PostgreSQL 17: отозванный получатель не проходит delivery fence, старый токен lease не подходит, исчерпанные попытки переводятся в `dead`, повторная очистка идемпотентна, браузерные роли не получают EXECUTE.
- Восстановление отдельной PostgreSQL-базы из custom `pg_dump` проверяет RLS, приватность читателей, финальные состояния уведомлений и отсутствие восстановления отменённых операций. Повреждённый архив должен быть отвергнут.

## Источник приёмки

- [CI R157 — тесты подписей, HTTP и реальной PostgreSQL](https://github.com/osmanosmanov6880-bot/marcosa-fusion/actions/runs/44213557259): **SUCCESS** для основных тестов и PostgreSQL-очистки контекста.
- Отдельный расширенный workflow проверяет также R157 custom dump/restore, повреждённый дамп и повторную изоляцию данных.
- Существующие R155/R156 схемы и CI не меняются за исключением новых зависимых модулей R157.

## Что блокирует реальный запуск

1. Подключение к настоящему Supabase Auth: подтверждение подписывающих ключей по доверенной конфигурации, интроспекция `session_id` с отзывом, безопасное обновление ключей и короткоживущие токены.
2. Отдельный наименее привилегированный **серверный** пул PostgreSQL с TLS/сертификатами, secrets manager и реальной проверкой прав; никаких суперпользовательских или service-role ключей в браузере.
3. Полный end-to-end реальный HTTP → подтверждённая сессия → PostgreSQL без моков (в изолированном staging); нагрузочные тесты, аудит и разрешения владельцев.
4. Настоящий поставщик уведомлений с recipient eligibility до внешней отправки, согласием, DLQ, восстановлением и отсутствием утечки персональных данных.
5. Независимый security-review, disaster recovery с настоящим резервным хранилищем, законность реальных платежей и авторских выплат.

**Вердикт:** только после независимой проверки интеграций. `main` и работающий сайт MARCOSA в этом цикле не менялись.
