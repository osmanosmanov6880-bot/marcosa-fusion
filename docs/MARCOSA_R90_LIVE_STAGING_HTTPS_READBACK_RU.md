# MARCOSA R90 — подтверждение реально выданной сборки STAGING по HTTPS

**Ключевое различие:** успешный GitHub Actions, создание архива, загрузка файла по SSH и правильный символический указатель \`current\` НЕ доказывают, что конечный пользователь получает именно этот релиз по HTTPS. R90 закрывает этот разрыв измеряемой проверкой **фактически отданных байтов**. Без проверенного внешнего сервера R90 — готовый инструмент, а не уже проверенный production.

## 1. Доказательство внутри публичного STAGING-архива

Сборка \`.github/workflows/marcosa-staging.yml\` после всех тестов вызывает:

\`\`\`bash
node ops/staging-release-attestation.mjs \
  --sha "$GITHUB_SHA" \
  --manifest dist/build-manifest.json \
  --output dist/staging-release.json
\`\`\`

\`staging-release.json\` содержит только публичные метаданные: \`sourceSha\` (полный HEAD коммита), \`buildManifestSha256\`, количество файлов, \`public_static_preview_only\` и \`productionAuthorized=false\`. Никаких ключей, паролей или содержимого пользовательской БД. Файл создаётся только один раз с запретом перезаписи.

При SSH-активации существующие host-key проверки, раздельная роль \`marcosa-deploy\` и атомарный release не отключаются. Дополнительная проверка **активной файловой системы** сопоставляет коммит, JSON, хэш \`build-manifest.json\` и фактические файлы \`index.html\`, \`network.js\`, \`network.css\`. Ошибка блокирует успешную активацию и запускает предусмотренную STAGING-only процедуру отката.

## 2. Независимая HTTPS readback-приёмка

На ревьюером подтверждённом HTTPS-домене (не секрет и не содержимое PR) запускается отдельная команда:

\`\`\`bash
node ops/staging-live-readback.mjs \
  --origin "https://YOUR-APPROVED-STAGING-HOST" \
  --host "YOUR-APPROVED-STAGING-HOST" \
  --sha "EXACT40_REVIEWED_AND_DEPLOYED_SHA" \
  --manifest-sha256 "EXPECTED64_FROM_TRUSTED_GITHUB_BUILD_ARTIFACT"
\`\`\`

Что проверяется действительно **по HTTP-ответам**, а не по логу деплоя:
- HTTPS и совпадение DNS имени с независимым параметром \`--host\`; запрет HTTP, пути, credentials, localhost, IP-литералов, нештатных портов и редиректов;
- реальный код 200, подходящий \`Content-Type\`, ограниченный размер, \`Cache-Control: no-cache\`, параметр запроса с точным SHA для избежания старых кешированных URL;
- обязательный \`staging-release.json\` с точным SHA, проверка статуса \`productionAuthorized=false\`, контроль \`buildManifestSha256\`;
- реальное чтение \`build-manifest.json\`, сравнение его SHA-256 с аттестацией;
- скачивание и SHA-256 **трёх реальных выданных файлов** — \`index.html\`, \`network.js\`, \`network.css\` — в сравнении с подлинным манифестом, отказ при одном устаревшем, подменённом или неожиданном файле.

Если это не выполнено, ответ \`verified:false\`, код возврата 2. Если выполнено, \`verified:true\` означает **только** подтверждение статического STAGING HTTPS на данном SHA, не успешную проверку пользователей, PostgreSQL, Storage или коммерческого запуска.

## 3. GitHub Actions / зона доверия

\`.github/workflows/marcosa-r90-staging-readback.yml\`:

- На PR и push проверяет реальными Node22-тестами генерацию, недоверенные данные, подменённые хэши, отсутствие overwrite, MIME, SSRF-подобные URL, запрещённые редиректы, ограничение ответа и точный SHA.
- По **ручному** \`workflow_dispatch\` из доверенной \`main\` и через защищённое окружение \`marcosa-staging\` может проверить внешний сайт, но только если владелец настроил защищённые переменные \`MARCOSA_STAGING_ORIGIN\` и \`MARCOSA_STAGING_PUBLIC_HOST\` в том же окружении. Из PR-параметров они не берутся.
- Обязательная независимая проверка в хостинг-панели: DNS/HTTPS и SSH ED25519 fingerprint принадлежат тому самому хосту, секреты и ключи известны уполномоченному оператору. Ручной запуск readback не создаёт сайт и не выполняет SSH.

Если окружение, настоящий hostname или опубликованный архив отсутствует, проверка должна завершиться **BLOCKED**, а не зелёной ложной статистикой.

## 4. Не является достаточным для запуска в мир

Даже публично совпадающий SHA не доказывает:
- конфигурацию работающего Supabase/Auth/JWT/RLS;
- приватность Storage, действительность утверждений о правах и отзыв старых signed URLs;
- реальную закрытую бету с согласием и D7/D30;
- отдельный юридически одобренный merchant и настоящие оплаты;
- полноту Disaster Recovery для PostgreSQL/Storage, независимую безопасность и RTO/RPO;
- подлинность автора доказательства, ownership DNS или фактическое решение независимого release owner.

Для мирового production по-прежнему требуется R48/R80 с \`productionAuthorized=false\` до отдельного письменного go/no-go по Issue #55. Не нужно присылать в чат SSH-ключи, токены, пароли или реальные пользовательские данные.

**Статус внедрения:** код/CI в GitHub, реальная приёмка внешнего STAGING **не проведена**, пока отсутствует проверенный адрес/доступ.

## R90: независимая привязка к CI

Публичный сервер способен подменить все пять файлов и заявленный SHA согласованно. Поэтому оператор должен получить `buildManifestSha256` **из GitHub Actions артефакта конкретной проверенной сборки**, а не из опубликованного по HTTPS JSON. Доверенный build job сохраняет `staging-expected-<GITHUB_SHA>.json` вне webroot в артефакт `marcosa-site-<GITHUB_SHA>`. Только его digest допустимо вставлять в обязательное поле `manifest_sha256` при ручном запуске R90 readback. При отсутствии независимого digest — BLOCKED; успешный HTTPS сам по себе не разрешает production.
