# MARCOSA R131 — независимый кластер PostgreSQL 17: настоящий аварийный restore

Дата: 26 октября 2026. **Только synthetic CI / production NO-GO.**

## Зачем

R128 и R130 восстановили настоящую PostgreSQL 17 `pg_dump -Fc` резервную копию и два файла Storage с проверкой SHA-256. Однако R128 восстанавливал таблицы во **вторую базу того же PostgreSQL-кластера**. Это не доказывает, что восстановление будет успешным после полной потери исходного сервера. R131 добавляет более сильную, полностью изолированную инженерную проверку.

## Проверяемые реальные операции

1. GitHub runner сперва завершает прежние R30–R84, R128 и R130. Проверяет, что два ограниченных исходных JSON отчёта действительно заявляют синтетические данные и `NO_GO`.
2. Через `pg_dump -Fc` получает **новую реальную** резервную копию PostgreSQL 17 с теми же синтетическими тестовыми данными. Вычисляет SHA-256, сохраняет архив временно с правами `0600`, не публикует backup.
3. Создаёт **совершенно новый Docker-контейнер PostgreSQL 17** из уже загруженного образа `postgres:17-alpine`, с `--network none`, без портов, SSH, DNS и подключения к Supabase. Проверяет `pg_control_system().system_identifier`: идентификатор нового кластера обязан отличаться от источника.
4. В независимом кластере создаёт *только* две модели глобальных ролей `anon` и `authenticated`, которых нет внутри `pg_dump -Fc`, и чистую базу `marcosa_r128_restored`.
5. Выполняет `pg_restore --exit-on-error --no-owner`. **Не отключает ACL**: права, запреты доступа и RLS входят в проверку.
6. Сравнивает счётчики шести таблиц между двумя физически разными кластерами. В отдельном кластере исполняет `tests/postgres/130_pg17_restore_rls_isolation.sql` и `tests/postgres/131_r130_restored_storage_acl.sql`: реальные SQL проверки приватных World/posts, межпользовательской изоляции, доступа `anon`, модерации и запрета чтения частных ключей.
7. По-настоящему считывает восстановленные SQL-записи медиа из нового контейнера и связывает `storage_key`, SHA-256, байты, размеры, владельца, reviewer и приватность с двумя физически восстановленными PNG R130.
8. Удаляет второй контейнер и архив. Публикует **только** ограниченный JSON с результатом `NO_GO`, без system identifier, паролей, SQL-дампов, исходных файлов, JWT и персональных данных.

## Обязательные отказы

Релизный тест должен отказать, если исходный и новый PostgreSQL имеют один системный ID, разную основную версию, расходящиеся счётчики, неправильный SHA, пропавшие PNG, неверного владельца/проверяющего, плохие RLS/ACL или отсутствующие R128/R130-артефакты. Нельзя считать восстановление на том же PostgreSQL-кластере достаточным.

Отдельные негативные тесты `tests/r131_isolated_pg17_cluster_restore.test.mjs` охватывают эти случаи. Скрипт исполняется только при `GITHUB_REPOSITORY=osmanosmanov6880-bot/marcosa-fusion` и локальном одноразовом `PGHOST=127.0.0.1`, без произвольных параметров.

## Чего R131 не доказывает

- Это по-прежнему **синтетические пользователи и PNG**; настоящий Supabase, Storage API/S3 и Auth JWT в опыте не участвуют. PostgreSQL общий каталог глобальных ролей подготовлен моделью фикстур.
- Изолированный кластер без сети проверяет архив, таблицы, роли, RLS и файлы, но не DNS, TLS, долговременную offsite-доступность, PITR или сценарий реального failover клиентского приложения.
- Новый README или зелёный CI никогда не заменит полную резервную копию **фактических** пользователей, Auth/Postgres/Storage, изолированное восстановление на стороннем оборудовании, 2+ настоящих staging аккаунта и законное согласие владельца.
- Нельзя менять `marcosa.club`, текущий production webroot, Nginx, DNS, живую базу и реальные учётные записи. R117 → два R118 → два R121 → R122/R127 по одному актуальному SHA обязательны отдельно.

Для реального GO нужны доступ к существующему Supabase/PG/Storage проекту, проверка legacy модулей issue #135 и явное разрешение владельца. До того **production NO-GO**.

Файлы: `ops/r131_isolated_pg17_cluster_restore.mjs`, `tests/r131_isolated_pg17_cluster_restore.test.mjs`, обновлённый `.github/workflows/marcosa-postgres-rls-reference.yml`.

## Точная атрибуция SHA GitHub Actions

В Pull Request `GITHUB_SHA` обычно является временным тестовым merge-коммитом, а не SHA исходного PR и не доказательством состояния текущего `main`. R131 фиксирует `shaOrigin=github_pr_or_other_ci_ref` для такого запуска; событие, пришедшее именно с `refs/heads/main`, получает `github_main_ref_event`. Поле `currentMainShaIndependentlyReverified` **всегда false**, потому что R131 не сравнивает HEAD с новым удалённым `main` и вообще не является полноценной реальной аттестацией R116–R122. ZIP из PR нельзя переименовать в доказательство нового production SHA.
