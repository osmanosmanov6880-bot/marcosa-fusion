# MARCOSA R31 — настоящие события и аналитика World

**Статус:** локальная серверная лаборатория Node.js/SQLite. Ни оплата рекламы, ни массовая регистрация на публичном GitHub Pages не запущены.

## Зачем
Пользователь возвращается не ради несуществующих метрик, а когда в его мире произошло полезное событие: подписка, ответ, предложение сотрудничества. R31 закрывает первоначальную техническую основу этой петли.

## Что реализовано
- Отдельная таблица notifications, привязанная к получателю и реальному участнику, с состоянием read_at, индексами для inbox и непрочитанных событий.
- Атомарные SQLite-триггеры на настоящие операции: новая подписка, новый комментарий к опубликованной записи, рекламное предложение и решения по нему. Дубликат подписки не создаёт второго события.
- GET /api/me/notifications: приватные записи только для текущего пользователя, cursor pagination, unread count из SQLite.
- POST /api/me/notifications/read: отметить до 30 выбранных ID прочитанными, только для владельца уведомлений; попытки изменить чужие ID не работают.
- GET /api/me/insights: реальные числа по собственным Worlds — опубликованные записи, приватные черновики, подписки, ответы, уникальные участники обсуждений. Нет фиктивных рекламных просмотров или доходов (поля null).
- Интерфейс в левом личном кабинете: «События в моих мирах», непрочитанное, дата, кнопки обновить/отметить; «Статистика моих миров». Все имена и подписи отображаются только через textContent.
- Регрессия существующих R28/R30 функций: приватность, закрытый вход по приглашению, жалобы, экспорт/удаление, рекламный отзыв согласия.

## Что НЕ реализовано и почему
- Push-уведомления, email-рассылка, спамящие reminders, коммерческие «1M просмотров», автоматические охваты и транзакции — нет.
- Действующий R28/R30 сервер привязан к loopback; эта функция недоступна реальным публичным пользователям.
- Механизм событий SQLite здесь используется как атомарная **проверка продуктового контракта**. Для боевой версии нужна production identity, Postgres/RLS, очередь/ретраи, политика хранения, антиспам, наблюдаемость и проверка сторонних акторов.

## Проверяемое определение готовности
1. Новое World follow пользователя B создаёт ровно одно событие пользователю A; повторное follow не увеличивает количество.
2. Комментарий B к опубликованной истории A создаёт ровно одно уведомление. Черновик недоступен для чужого комментирования.
3. Спонсорский proposal → согласие владельца → независимая проверка создают события только у реальных сторон сделки; без оплаты и рекламного охвата.
4. B не получает inbox A, не может пометить его записи прочитанными; гость получает HTTP 401.
5. Проверенные counts в insights совпадают с фактическими SQLite строками; уникальные комментаторы не множатся от повторных ответов.
6. На ПК/мобильных реальная форма уведомлений показывает данные, возможность прочитать и достоверные числа.
7. Действующий public Pages остаётся нетронутым. Слияние PR только после успешного GitHub Actions.

**Дальнейший gate:** существующий Supabase-проект отсутствует в доступном подключении, а отдельный STAGING требует проверки SSH host key. Без них R31 нельзя объявлять публичным multi-user релизом.
