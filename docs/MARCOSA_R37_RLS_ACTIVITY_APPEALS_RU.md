# MARCOSA R37 — реальные SQL-права для уведомлений и апелляций

**Статус:** тестируемый Postgres-контракт для проверки в disposable CI, а не выполненная миграция существующего Supabase-проекта.

## Зачем создан этот этап

R30 дал базовые шесть таблиц (профили, Worlds, публикации, подписки, комментарии и закрытые рекламные заявки). R31 добавил приватные уведомления, R32 — независимую модерацию. Без дополнительных RLS эти новые возможности нельзя безопасно переносить в реальный многопользовательский Postgres.

## Что вошло

- `public.marcosa_activity_events`: уведомления о действительно совершённых действиях с внешним ключом на получателя и автора события, составными индексами и `read_at`.
- RLS: подписавшийся человек видит только **свои** уведомления и может изменять исключительно `read_at` собственных строк. Нельзя переделать получателя, тип, автора или дату события через клиент.
- `public.marcosa_moderation_appeals`: личные апелляции; уникальная открытая апелляция на один пост/комментарий, явный статус и связь с проверяющим.
- RLS: посетитель не видит чужие причины жалоб. Браузер **не получает права** создавать, удалять или разрешать обращения — проверку авторства, статуса скрытия и независимого модератора обязан выполнять доверенный сервер.
- `marcosa_private.moderation_audit`: закрытый журнал решений в private-схеме; нет браузерных GRANT и нет открытых политик.
- Отдельный SQL-тест с аккаунтами Alice/Bob/Carol: читаются только собственные данные; подделка события и апелляции запрещена; метка прочтения изменяется только владельцем; аудит не раскрыт.

## Порядок CI

1. PostgreSQL 17 Alpine стартует на локальном порту GitHub runner.
2. Тестовый fixture создаёт имитацию трёх JWT identity/ролей **только в CI**.
3. Запускается R30 SQL, затем R33 базовая SQL-проверка.
4. Запускается R37 расширение и `tests/postgres/20_rls_activity_appeals.sql`.
5. GitHub Actions должен завершить все SQL-операции без ошибок.

## Что остаётся до production

1. Подключённый Supabase пока возвращает пустой список проектов. Нельзя выполнить настоящее развертывание, анализ политик Security Advisor, проверить реальный OAuth/email verification и права живых клиентов.
2. Доверенные backend-маршруты создания событий, подтверждения авторства апелляций, действий модератора и бизнес-процессов R31-R32 для Postgres **ещё не реализованы**. SQL отражает нужную модель разрешений.
3. Нет доставки email/push, полноценной очереди и юридически завершённой политики модерации.
4. Нет защищённого удалённого staging: проверка SSH host key обнаружила mismatch, обход категорически запрещён.

**Правило:** не загружать production-данные в CI и не выдавать этот SQL за готовую миграцию. Переносить только после инвентаризации существующей БД, backup/restore и отдельных интеграционных испытаний с реальными JWT.
