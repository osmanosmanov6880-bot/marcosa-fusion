# MARCOSA R177 — неизменяемая история и доказательства после восстановления

19 ноября 2026 · PR #168 · ветка `feature/marcosa-r150-growth-economics`.

## Пять полноценных инженерных блоков

1. **Native PostgreSQL17 append-only свидетельства** — R177 schema 178: 5 таблиц для архива, аудита, цепочного корня, результата и его аудита. FORCE RLS, NOLOGIN NOBYPASSRLS writer, только SELECT/INSERT, без UPDATE/DELETE. Каждая версия сверяется с реальным R174 архивным event и подписанным predecessor. SQL-вычисление хешей не заменяет криптопроверку; подписи проверяет R176 до доверенной записи.
2. **Полная offsite reconciliation** — точно закреплённые S3 objectVersionId, полный HEAD/GET, Ed25519 от двух отдельных ключей, SHA256 каждого предка, независимое чтение R174 перед и после, запись в PG17 и проверка по отдельно прочитанному журналу. Никакого обращения к исходному AWS, «latest» или автоматического возобновления.
3. **Криптографический root и аттестация восстановления** — SHA-256 канонических данных истории, единственная запись root для sequence, append-only результат связан с R176 nonce, R174 high-water, root и точным S3 объектом. Без подтверждённой проверки целевой восстановленной базы успех невозможен.
4. **Fail-closed recovery controller** — отдельная R176 последовательность допуска/restore, повторная проверка R174, обязательные native PG17 readback/forced RLS/replay checks, сверка записи результата отдельным чтением, кодированный инцидент на любой ошибке.
5. **Реальный PG17 CI и второй независимый runner** — настоящая миграция и CAS seq=3, реальные R175/R176 однократные допуски, native pg_dump -Fc и два независимых pg_restore, чтение неизменяемой истории/аудита, отказ при повторе, приватность и RLS; второй runner не получает PG-секретов, заново считает source manifest и проверяет формальную SHA-схему не-секретного readback.

## Честные ограничения

CI использует **реальный одноразовый PostgreSQL17**, но **синтетические** AWS S3/KMS/STS ответы, временные Ed25519 ключи и тестовых пользователей. В CI нельзя доказать личности независимых людей, действительную репликацию S3, эффективные IAM-права, продакшн RPO/RTO, пригодность Supabase и реальный коммерческий запуск. Отчёт не является независимым аттестатом реального провайдера. `productionAuthorized=false`. Сайт, main, реальные платежи, пользовательские базы и AWS не менялись.

Принятие требует SUCCESS обоих jobs workflow R177 на последнем commit SHA PR.
