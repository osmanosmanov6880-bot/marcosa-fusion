# MARCOSA R155 — PostgreSQL 17: инженерная приёмка перехода, без production

Статус: реализация в [PR #168](https://github.com/osmanosmanov6880-bot/marcosa-fusion/pull/168), ветка `feature/marcosa-r150-growth-economics`. **Никаких подключений к настоящему Supabase/VPS, пользовательских баз, платежей или банковских выплат.**

## Пять полноценных инженерных блоков

### 1. PostgreSQL 17, шесть таблиц и защита связей
- Файл: `docs/MARCOSA_R155_PG17_CREATOR_RLS_REFERENCE.sql`.
- Сезоны, эпизоды, подписки, закладки, добровольные отметки, журнал редактора.
- Индексы, проверка максимальной длины, FK с каскадами, запрет приписать мир или чужой/неопубликованный пост другому автору.
- Это **отдельная reference-схема**, а не автоматически применяемая миграция. Зависимости: R30 auth/world/post, R41 private block roster и R84 проверенная приватная eligibility-функция.
- Временно запрещены *все прямые записи клиента* в эти таблицы: только `SELECT` по RLS. Реальный серверный backend/transaction API остаётся отдельным этапом.

### 2. Реальные RLS-проверки в PostgreSQL
- Файлы: `tests/postgres/155_creator_seasons_rls.sql`, `.github/workflows/marcosa-r155-pg17.yml`.
- Изолированная PostgreSQL 17, три независимых подставных пользователя.
- Проверяются: владелец/читатель/гость, архивирование, приватный мир, взаимные блокировки, запрет чужих закладок и журнала, отказ при запрещённых записях и подмене tenant, запрет прикрепления чужих постов и черновиков, каскадное удаление.
- Уязвимости проверяются **настоящими SQL-командами с `SET ROLE authenticated/anon`**, а не регулярными выражениями по исходнику.

### 3. Стабильный экспорт синтетического SQLite в PostgreSQL
- `ops/r155/migration-bundle.mjs`.
- Поддерживается только `:memory:`-база с явной отметкой `syntheticOnly:true`; файловый источник блокируется до чтения контента.
- Явное bijective соответствие исходного пользователя будущему UUID `auth.users`; **никогда** не создаёт и не переносит настоящие Auth-аккаунты.
- Стабильные UUIDv5 для миров, постов, сезонов, выпусков и аудита; проверка всех связей и ограничение на объём.
- Вынесены только нужные поля: не выводятся email, пароли, сессии, ключи, платежи и другие сведения соседних систем.
- `checksumSha256` подтверждает неизменность полезного JSON. **Это незаверенный хэш, не подпись происхождения**.

### 4. Реальный двукратный импорт и восстановление
- `ops/r155/pg-replay.mjs`, `ops/r155/disposable-fixture.mjs`, `tests/postgres/156_r155_restored_parity.sql`.
- Синтетический сценарий создаётся через настоящий loopback HTTP API и SQLite.
- SQL формируется безопасным экранированием строк, применяется только к локальной одноразовой PG17. Повтор с тем же содержимым допускается, конфликтующие поля проверяются на каждой строке и отвергаются.
- Отдельно проверяется невозможность пропустить незаметно подмену названия, затем выполняются `pg_dump --format=custom` и восстановление в новую PostgreSQL-базу.
- После восстановления повторно подтверждаются RLS, приватность читателя, архивные сезоны, история редактора, целостность пользовательских записей, строгая проверка SHA-256. Повреждённый архив отвергается.
- Это НЕ реальная миграция пользователей и НЕ готовый production-импорт.

### 5. Запрет перехода в production до независимой приёмки
- `ops/r155/cutover-gate.mjs`, `ops/test/r155.cutover-gate.test.mjs`.
- Шесть обязательных CI-свидетельств с привязкой к точному SHA.
- Независимый reviewer, настоящий Auth-мэппинг, реальные резервные копии, TLS/SSH pin, результаты восстановления и отдельный security-review.
- Без этих сведений -> `NO_GO`. Даже при подставленных успешных флагах возвращается только `ELIGIBLE_FOR_EXTERNAL_REVIEW_ONLY`, не производятся деплой, миграция или платёжная операция.

## Тестовые команды

```sh
node --test ops/test/r155.*.test.mjs
node ops/r155/cutover-gate.mjs
# В GitHub Actions (postgres:17-alpine) выполняются:
psql -v ON_ERROR_STOP=1 -f tests/postgres/155_creator_seasons_rls.sql
node ops/r155/disposable-fixture.mjs "$RUNNER_TEMP/r155-synthetic-replay.sql"
# Затем импорт дважды, проверка несовпадения и отдельный pg_dump/pg_restore
```

## Условия реального перехода

1. Выделить из пилота отдельный защищённый production backend и Auth; проверить авторизацию с настоящими JWT, обновлением/отзывом сессий, реальными `auth.users`.
2. Выполнить новую миграцию через подходящий инструмент и независимый review, а не применять этот reference-SQL к действующей БД.
3. Тестовая карта UUID **не заменяет** пользовательскую идентичность: обязательны подтверждённые связи пользователей и проверка авторских прав.
4. Доказать восстановление настоящего независимого encrypted/offsite бэкапа, GDPR/retention, IP/TLS и rollback без потери пользовательских данных.
5. Пройти аудит безопасности, налогов и платёжного провайдера. Настоящие платежи и выплаты авторам по-прежнему **не подключены**.

Ни один CI-тест не даёт сам по себе разрешения на production. Основной `main` и публичный сайт остаются неизменными.
