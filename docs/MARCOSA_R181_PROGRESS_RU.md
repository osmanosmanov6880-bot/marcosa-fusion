# MARCOSA R181 — реальный read-only контур staging и NO-GO до независимой приёмки

19 ноября 2026 · PR #168 · feature/marcosa-r150-growth-economics

## Пять крупных реализованных блоков

1. **Read-only GitHub Environment и действительная политика ветки.** `ops/r181/github-policy-inspector.mjs` отправляет исключительно GET запросы к точной среде `marcosa-aws-staging`, защите текущей ветки, workflow run и его истории /approvals. Требует отсутствия самоодобрения, strict status checks, защиты администраторов/force-push, не менее двух PR approving reviews и **двух фактических событий deployment approval** от разных User ID. Отказ 403/404 и любые отсутствующие права закрывают приёмку. Назначение нескольких required reviewers **само по себе не означает, что оба одобрили deployment**.
2. **Реальный read-only AWS CLI адаптер.** `ops/r181/aws-readonly-cli.mjs` выполняет строго ограниченные команды `aws sts get-caller-identity`, `aws s3api get-bucket-replication/get-bucket-versioning/get-object-lock-configuration/get-public-access-block/head-object/get-object-retention/get-object` для **двух разных именованных AWS profiles**. Никаких shell интерполяций, AWS writes или KMSDecrypt напрямую. Обязательно должны быть действительные read-only роли. S3 GET с SSE-KMS может требовать `kms:Decrypt` в обоих аккаунтах; ответ содержит исходные **прикладные AES-GCM данные** после серверного SSE-KMS расшифрования, а не физический SSE-KMS ciphertext. Каждый объект через точный VersionId, SHA-256 всех прикладных байтов, COMPLIANCE, срок хранения, требуемые метаданные и статусы COMPLETED/REPLICA; загрузка в закрытую временную папку с очисткой.
3. **Строгий staging evaluator и ручной CLI.** `ops/r181/staging-evaluator.mjs` требует неизменяемый R180 NO-GO, закрытый карантин, двойное чтение R180 до/после двух внешних проверок, TTL доказательств и соответствие commit/bundle/hash. `ops/r181/manual-preflight.mjs` даёт реально исполнимый **только вручную** read-only запуск при наличии подтверждённого source SHA, GitHub read-only token, ожидаемых review user IDs и AWS профилей. Он никогда не публикует, не раскрывает токены, не открывает карантин; решение — `NO_GO_PROVIDER_ATTESTATION_PENDING`.
4. **Реальный PostgreSQL 17: неизменяемый реестр наблюдений.** `tests/postgres/182_r181_readonly_observations.sql`, `ops/r181/observation-ledger.mjs`: `SERIALIZABLE`, `FORCE RLS`, `NOLOGIN` только INSERT/SELECT, уникальный одноразовый run/nonce и FK+JOIN на точную R180 hold и audit. Запрещены UPDATE/DELETE и доступ authenticated. Только решение NO-GO, отличные SHA-256 источника и observed app-encrypted probe.
5. **CI с отказами и независимой проверкой.** `ops/test/r181.readonly.test.mjs` проверяет запрещённую GitHub branch API, подмену reviewers, продублированные approvals, неправильные S3 версии/байты/KMS/TTL/STS, гонку PG, повтор записи и запрет AWS CLI mutating operations. `ops/r181/ci-acceptance.mjs` использует **одну и ту же** зашифрованную R178 тестовую копию, настоящий disposable PG17 с `pg_dump -Fc/pg_restore` и отдельный runner без credentials, который восстанавливает source SHA и проверяет запрет fake staging GO.

### Как запустить реальную read-only проверку вручную

Нужны AWS CLI v2 и две отдельные read-only AWS profiles, GitHub token c достаточными правами read для environments/branch protection/run history, явные параметры `R181_SOURCE_*`, `R181_OFFSITE_*`, `R181_GITHUB_RUN_ID`, `R181_GITHUB_ACTOR_ID`, `R181_REVIEWER_IDS`, `R181_SOURCE_COMMIT`, `R181_BUNDLE_SHA256`, `R181_HISTORY_ROOT_SHA256`, `R181_APPLICATION_ENCRYPTED_OBJECT_SHA256`, `R181_SOURCE_VERSION_ID`, `R181_OFFSITE_VERSION_ID`. Токены/ключи в PR не добавлять и в чат не вставлять. После установки переменных `R181_ALLOW_READONLY=YES_MANUAL_NO_DEPLOY` запустить `node ops/r181/manual-preflight.mjs --read-only` из checkout точного commit. Скрипт не взаимодействует с БД и не снимает NO-GO.

### Ограничения

Этот CI использует реальный одноразовый PostgreSQL17, но **синтетические GitHub/AWS API ответы**. Коннектору сейчас недоступно чтение защищённых настроек GitHub Environment и branch protection. Без read-only доступа и независимой проверки внешнего провайдера, личности двух людей, RPO/RTO и приватности этот проход **не является реальной staging-приёмкой**. Даже если ручная read-only проверка проходит, доступна лишь диагностика; отсутствие независимой attestation оставляет NO-GO. `main`, сайт, реальные AWS/клиентские данные и платежи не менялись.

Приёмка R181: два SUCCESS jobs workflow на точном SHA; это **техническая** приёмка, не production GO.
