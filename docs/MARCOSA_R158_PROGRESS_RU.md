## Пять полноценных инженерных блоков

### 1. Сессионная база и разграничение привилегий

Файлы: docs/MARCOSA_R158_SESSION_BOUNDARY_REFERENCE.sql, tests/postgres/163_r158_roles_and_fixture.sql.

- Приватные сессии с expires_at и revoked_at, ссылкой на auth.users, ограничениями и RLS.
- Отдельная роль session-reader: NOLOGIN, NOBYPASSRLS, только SELECT.
- anon, authenticated, writer и dispatcher не имеют прав читать хранилище сессий.
- Одноразовая LOGIN-роль маркера CI с NOINHERIT/NOBYPASSRLS может только временно принять доверенную роль. Прямое чтение сессий и выполнение команды без смены роли отвергаются.
- Каждая операция проходит проверку действительности session_id. Отозванная и недоступная сессия -> отказ в доступе.
- Важная граница: синтетическая таблица НЕ заменяет реальную проверку Supabase Auth.

### 2. Изолированный backend транспорт до реальной PostgreSQL

Файл: ops/r158/psql-command-adapter.mjs.

- SQL через настоящий psql, Node spawn без оболочки и без интерполяции произвольных пользовательских SQL.
- Для каждой команды отдельное соединение и транзакция BEGIN/SET LOCAL ROLE/временный actor claim/COMMIT.
- 7 заранее разрешённых SQL-функций R156; UUID, строковые поля, boolean, порядок и revision проходят строгую проверку.
- Произвольный текст кодируется в hex, затем восстанавливается как UTF-8 внутри PostgreSQL, а не вставляется в SQL-синтаксис.
- Привязка к конкретному GitHub Actions repository, PGHOST=127.0.0.1, PGDATABASE=postgres и непривилегированному пользователю CI. При несовпадении конфигурации выполнение блокируется.
- Тайм-ауты и ограничение вывода. Внешние SQL-сообщения не выдаются в HTTP-ответ.
- Транспорт предназначен только для CI и НЕ является production-grade пулом с TLS.

### 3. Настоящие подписанные HTTP-команды

Файл: ops/r158/e2e.mjs.

- Внутри CI генерируется собственный временный ES256 JWT, который проходит проверенный R157 verifier.
- HTTP: строгий Origin, Authorization, Idempotency-Key, JSON. Сеансы подтверждаются реальным PostgreSQL SELECT через специальную роль.
- Семь операций: изменение названия/описания, перестановка, публикация нового эпизода, архивирование, подписка, закладка, добровольная отметка просмотра.
- Два независимых пользователя и посторонний аккаунт: проверка чужого редактирования, архива, токена с запрещённой ролью и чужого Origin.

### 4. Проверка повторов, гонок и отзыва согласия/сессии

Файлы: ops/r158/e2e.mjs и ops/test/r158.contract.test.mjs.

- Однократное применение idempotency-key, повтор с исходным ответом и запрет изменения payload с тем же ключом.
- Два реальных HTTP-запроса используют два отдельные PostgreSQL соединения: только один проходит на старой ревизии.
- После снятия сезона с публикации очередь не восстанавливает запрещённые уведомления.
- Собственная закладка и добровольная отметка удаляются после архивирования.
- Отзыв session_id в базе -> следующая HTTP-команда даёт 401. Счётчик принятых команд пользователя не меняется.
- Недоступная сессионная БД -> fail-closed. Незнакомые функции, неверные UUID, удалённый хост или postgres-superuser запрещаются до обращения к сети.
- Модульная часть: 3/3 теста; сквозная часть — реальные HTTP-вызовы.

### 5. Настоящий PG17 dump/restore и автоматическая приёмка

Файлы: .github/workflows/marcosa-r158-integration.yml, tests/postgres/164_r158_restored.sql.

- Одноразовый postgres:17-alpine, полностью поднятый R30/R41/R84/R155/R156/R157.
- CI заново подтверждает RLS, роли, выполнение семи HTTP-команд и отказ при отзыве сессии.
- Создаётся настоящий pg_dump custom, проверяется SHA-256, поднимается новая БД marcosa_r158_restored, затем выполняется pg_restore.
- После восстановления проверяется ровно 5 ревизийных действий и 5 записей аудита, состав эпизодов, точность журнала команд, отозванная сессия, отсутствие удалённых отметок и видимость архивного сезона исключительно владельцу.
- Повреждённый архив отвергается. Исходный дамп и исходная база не перезаписываются.
