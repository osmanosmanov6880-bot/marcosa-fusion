# MARCOSA R48 — доказательный релизный контроль: STAGING → закрытая бета → PUBLIC

Этот этап превращает критерии [выпуска #55](https://github.com/osmanosmanov6880-bot/marcosa-fusion/issues/55) в **выполняемый проверочный контракт**. Он не открывает сеть, не устанавливает Supabase, не меняет SSH, не создаёт платежи и не заменяет независимую приёмку.

## Реализованные проверки

В `ops/check-release-gate.mjs` три профиля:

| Профиль | Что требуется |
|---|---|
| `staging` | SSH host key подтверждён независимо, настоящий HTTPS/TLS, изоляция, минимальные права, проверенный откат и восстановление |
| `beta` | Всё из staging плюс действующий Supabase, Auth с верификацией, JWT/RLS испытания разных пользователей, модерация/апелляции, экспорт/удаление, управляемые приглашения, пользовательское согласие, реагирование на инциденты |
| `public` | Всё из beta плюс доступность, нагрузка, юридические условия, идентификация рекламодателя, реально подтверждённая доставка рекламы, платежи/возвраты, результаты настоящей беты и независимый аудит безопасности |

У каждого пункта: `status: verified`, `artifact` как защищённая HTTPS-ссылка на доказательство, `checkedAt` в ISO-формате и `reviewer`. Подтверждения SSH host key и TLS считаются устаревшими через 30 дней, прочие — через 90 дней. Ссылки с паролями, встроенными секретами, URL-query, на localhost и небезопасные протоколы отклоняются. Проверяется **полный 40-символьный SHA коммита**.

### Ключевое ограничение доверия

Эта программа **не может проверить истинность внешней ссылки или полномочия указанного reviewer**. Даже когда все поля валидны, результат `READY_FOR_INDEPENDENT_REVIEW` означает только готовность документов к независимому просмотру, а поле `productionAuthorized` **всегда** равно `false`. Для выпуска обязателен отдельный акт владельца проекта и независимого проверяющего. Никакой автоматической публикации на основании этого JSON не существует.

## Как работать

1. Оператор получает независимые доказательства и проверяет внешние системы: Supabase project, SSH fingerprint из панели хостинг-провайдера, HTTPS, backup restore, JWT/RLS, настоящие пользователи и договоры.
2. Создаёт приватный реестр доказательств; в репозитории `ops/release-evidence.json` — **только пустая fail-closed заготовка**. **Не добавлять** учетные данные, SSH private key, environment-файлы, seed-фразы и реальные персональные данные.
3. После проверки и при необходимости безопасного обновления evidence JSON запускает `node ops/check-release-gate.mjs --profile staging --evidence ops/release-evidence.json --sha <CURRENT_FULL_COMMIT_SHA>`. Для иных этапов профили `beta` и `public`. Успешный результат никогда не снимает требование независимой подписи.
4. `.github/workflows/marcosa-r48-release-gate.yml` автоматически проверяет 7+ негативных сценариев и доказывает, что пустые доказательства **не проходят**. Ручной GitHub workflow_dispatch только проверяет выбранный профиль; он **не публикует** и **не меняет production**.
5. Если доказательства отсутствуют — решение `BLOCKED`, прекращаем продвижение релиза. Не подменять host key, не запускать с `StrictHostKeyChecking=no` и не объявлять статический preview настоящей соцсетью.

## Что сейчас реально известно

- Локальная MARCOSA R45 успешно прошла API/Chromium QA на Node 22, но это не Supabase Auth.
- R46 проверен на одноразовом disposable PostgreSQL 17, но **не развёрнут** в подключённом Supabase.
- На момент R48 подключение Supabase показывает `projects: []`.
- STAGING имеет отдельный стоп-фактор проверки SSH server host key, не разрешённый настоящей проверкой ключа из панели провайдера.
- Нет доказательств легальных платежей, рекламной доставки и значимых D7/D30 у реальных пользователей.

**Пока ни один профиль нельзя считать готовым к настоящему развёртыванию.** Этот блок приближает MARCOSA к инженерно управляемому выпуску, не создавая ложного статуса завершения.
